How the layers fit together

A request passes identity and authorization, then takes a controlled path to a hardened workload and its data. Governance sets the rules those resources must meet, and every layer reports to the people who watch and respond.

Remember

  • Prevention is the path from the top; detection and response are the bottom row. Scenarios usually say which they want: prevent, block, must not, or detect, alert, investigate.
  • Governance sits outside the request path, except Azure Policy, which evaluates create, update and delete requests.
  • Response usually ends back in governance: a tighter role, a new policy, a closed network path.

An admin changes something in Azure

Identity first, then authorization, then the checks Azure Resource Manager runs on the request itself.

flowchart TD
  accTitle: An admin changes something in Azure
  accDescr: The admin signs in to Entra ID. Conditional Access can block or require MFA. An eligible role is activated in PIM. Azure RBAC authorizes the action. A create or update meets Azure Policy and a delete meets resource locks. The change is written to the activity log and reaches Sentinel.
  A(["Admin opens<br/>the Azure portal"]):::actor --> B["Entra ID checks<br/>the first factor"]:::d01
  B --> C{"Conditional Access:<br/>any policy<br/>says Block?"}:::d01
  C -->|Yes| X1["Sign-in blocked"]:::stop
  C -->|No| C2{"Every policy's<br/>grant controls met?"}:::d01
  C2 -->|"No, e.g.<br/>MFA needed"| C3["Prompt for MFA,<br/>or deny"]:::warn
  C3 --> C2
  C2 -->|Yes| D{"Role already<br/>active?"}:::d01
  D -->|"No, only<br/>eligible"| D2["Activate it in PIM:<br/>MFA, justification,<br/>approval, time limit"]:::d01
  D2 --> E
  D -->|Yes| E{"Azure RBAC:<br/>action allowed<br/>at this scope?"}:::d01
  E -->|No| X2["AuthorizationFailed"]:::stop
  E -->|Yes| K{"Kind of<br/>request?"}:::d01
  K -->|"Create or<br/>update"| F{"Azure Policy:<br/>a Deny rule<br/>matches?"}:::d01
  F -->|Yes| X3["RequestDisallowedByPolicy"]:::stop
  F -->|No| H["Change applied"]:::ok
  K -->|Delete| G{"CanNotDelete or<br/>ReadOnly lock<br/>in scope?"}:::d01
  G -->|Yes| X4["ScopeLocked,<br/>even for Owner"]:::stop
  G -->|No| H
  H -.-> L["Activity log"]:::d04
  L -.->|"Azure Activity<br/>connector"| S["Microsoft Sentinel"]:::d04

Remember

  • Conditional Access has no priority order: a block in any policy wins, and every other policy's requirements must all be met.
  • PIM limits when a role is active, not what it can do. RBAC still decides the action.
  • A ReadOnly lock blocks updates too. Locks win over every role, Owner included.

An app reads a secret and a database

No password anywhere: the app's managed identity, a private path, and data-plane authorization at each service.

flowchart TD
  accTitle: An app reads a secret and a database
  accDescr: The app's managed identity gets a token from Entra ID. The request must arrive through the private endpoint because public network access is disabled. Key Vault authorizes with Azure RBAC. Azure SQL accepts the identity only if it is a contained database user. Defender plans watch both and alert to Defender XDR.
  A(["App Service app needs<br/>a secret and some rows"]):::actor --> B["Managed identity:<br/>Azure issues and<br/>rotates its credential"]:::d01

  D -->|"No: public network<br/>access is disabled"| X1["Refused: 403"]:::stop
  D -->|Yes| F{"Azure RBAC:<br/>Key Vault<br/>Secrets User?"}:::d01
  F -->|No| X2["403: caller is<br/>not authorized"]:::stop
  F -->|Yes| G["Secret returned"]:::ok
  G --> H{"Azure SQL: is it<br/>a contained user?"}:::d02
  H -->|No| X3["Login failed"]:::stop
  H -->|Yes| I["Rows returned"]:::ok
  G -.-> J["Defender for Key Vault<br/>and for Databases"]:::d04

  J -.->|alerts| K["Defender XDR<br/>incident"]:::d04

A request from the internet reaches your API

Each layer answers a different question, and each has its own way of saying no.

  accDescr: The WAF on Front Door or Application Gateway evaluates custom rules, then managed rules with anomaly scoring. API Management validates the token and applies a rate limit. App Service access restrictions check the source, and App Service authentication checks the user token. Logs go to Sentinel.

Traffic leaves a VM for the internet

Which rules decide, in which order, and how routing can skip the firewall entirely.

flowchart TD
  accTitle: Traffic leaves a VM for the internet
  accDescr: Virtual Network Manager security admin rules are evaluated first. Outbound, the NIC NSG is evaluated before the subnet NSG. Routing then decides. A service endpoint route goes straight to the Azure service. A default user-defined route sends traffic to Azure Firewall, which applies threat intelligence, network rules and application rules.

  B -->|"Allow, or<br/>no match"| C{"NIC NSG allows?<br/>outbound: NIC first"}:::d02
  C -->|No| X1
  C -->|Yes| D{"Subnet NSG<br/>allows it?"}:::d02
  D -->|No| X1
  D -->|Yes| R{"Which route<br/>wins?"}:::d02
  R -->|"Service endpoint<br/>route, to an<br/>Azure service"| S["Straight to the service:<br/>the firewall never<br/>sees it"]:::warn

An AI agent uses a tool

Guardrails screen content, the gateway meters the model, and the agent's own identity gets the token for the tool.

flowchart TD
  accTitle: An AI agent uses a tool
  accDescr: The agent's guardrail screens the user input. The agent calls the model through the AI gateway, which applies a token limit. When the model plans a tool call, the agent's own identity requests a token, which Conditional Access for agents can block. The guardrail screens the tool response for indirect attacks and the final output. Defender for AI Services alerts, Defender XDR shows the blast radius, and Purview DSPM sees sensitive data.
  A(["User asks<br/>the agent"]):::actor --> B{"Guardrail, user<br/>input: jailbreak?"}:::d03

  B -->|No| C{"Model call via the<br/>AI gateway: token<br/>limit exceeded?"}:::d03
  C -->|Yes| X2["429 from<br/>API Management"]:::stop
  C -->|No| D["Model plans<br/>a tool call"]:::d03
  D --> E0["The agent's own<br/>identity asks Entra<br/>for a tool token"]:::d01
  E0 --> E{"Conditional Access<br/>for agents<br/>blocks it?"}:::d01
  E -->|Yes| X3["No token:<br/>tool not called"]:::stop
  E -->|No| F["Tool runs, e.g.<br/>a search index"]:::d03
  F --> G{"Guardrail, tool<br/>response (preview):<br/>indirect attack?"}:::d03

  G -->|No| H{"Guardrail, output:<br/>harmful content?"}:::d03
  H -->|"Yes: block"| X5["Blocked"]:::stop

  B -.->|attempt detected| J["Defender for<br/>AI Services alert,<br/>with prompt evidence"]:::d04

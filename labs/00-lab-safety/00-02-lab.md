# Lab 00-02 - PIM-Based Just-in-Time Lab Access

**Objective:** Implement and configure Privileged Identity Management (PIM)
**Estimated cost:** Included in a Microsoft Entra ID P2 trial.
**Licensing required:** Microsoft Entra ID P2 or Microsoft Entra ID Governance.
**Time:** 60 minutes.

> Complete [00-01](./00-01-lab.md) first. This lab creates no billable resources,
> but it is the last step before you start doing so.
>
> **Ordering matters.** You configure eligibility, prove activation works, and
> *only then* remove your standing role. Reversing those steps is how people lock
> themselves out of their own tenant.

## Why this lab matters

A permanent administrator role is a standing target. If that account is phished, the
attacker inherits every permission at once, at any hour, with nothing to slow them down.
Privileged Identity Management (PIM) replaces standing access with eligibility: you hold the
right to switch a role on for a limited time, with a reason, and every activation is
recorded. This lab moves your own lab access to that model without locking you out.

## Architecture

```text
Your working account  (no permanent admin roles)
        |  eligible assignment
        v
PIM activation  --  MFA + justification + time limit
        |
        v
Active role for a few hours  -->  Entra roles / Azure resource roles
        |
        v
PIM audit history  (every activation and deactivation)

Break-glass accounts: permanent Global Administrator, kept outside PIM
```

*A teaching model of what this lab builds - not a complete deployment diagram.*

## Desired security outcome

When the lab is finished, each of these statements is true - and **Validation** proves it:

- Your working account holds zero permanent directory role assignments, and several eligible ones.
- An activation works end to end, and it appears in PIM audit history with the justification you typed.
- Only the emergency (break-glass) accounts still hold Global Administrator permanently.
- The Azure resource roles the labs need are eligible too, not standing.

## Prerequisites

- Microsoft Entra ID P2 licence assigned to your working account. Check under
  **Entra admin center** → **Billing** → **Licenses**.
- Two emergency access accounts created and their credentials stored outside the
  tenant. See [00-00](../../content/00-lab-safety/00-00-module-overview.md#lab-topology).
- MFA registered on your working account.
- Modules: `Microsoft.Graph.Identity.Governance`, `Microsoft.Graph.Users`,
  `Az.Resources`.

```powershell
Install-Module Microsoft.Graph -Scope CurrentUser
Connect-MgGraph -Scopes @(
    'RoleManagement.ReadWrite.Directory'
    'RoleAssignmentSchedule.ReadWrite.Directory'
    'RoleEligibilitySchedule.ReadWrite.Directory'
    'RoleManagementPolicy.ReadWrite.Directory'
    'User.Read.All'
)
```

> **Complete the MFA challenge during this sign-in.** Self-service PIM operations
> over Graph require a session in which MFA was actually performed, not merely a
> session belonging to an MFA-capable account. If activation later fails with an
> MFA error, this is why — disconnect and reconnect.

## Part 1 - Entra roles

### Method A - Portal

#### A1. Configure the activation policy *before* creating eligibility

The policy is the control. Setting it after you create eligibility means there is
a window where the role activates with no conditions.

1. **Entra admin center** → **Identity Governance** → **Privileged Identity
   Management** → **Microsoft Entra roles** → **Settings**.
2. Select **Security Administrator** → **Edit**.
3. **Activation** tab:
   - Activation maximum duration: **4 hours**
   - **On activation, require**: Microsoft Entra multifactor authentication
   - **Require justification on activation**: ticked
   - **Require ticket information on activation**: unticked
   - **Require approval to activate**: unticked
4. **Assignment** tab:
   - Allow permanent eligible assignment: **unticked**; expire eligible
     assignments after **6 months**
   - Allow permanent active assignment: **unticked**
   - **Require Microsoft Entra multifactor authentication on active assignment**: ticked
5. **Notification** tab: leave defaults on. You want to see what these look like.
6. **Update**.

Repeat for **Global Administrator**, with two differences: activation maximum
**1 hour**, and **Require ticket information on activation** ticked. Friction
belongs where the blast radius is largest.

#### A2. Create eligible assignments

1. **Privileged Identity Management** → **Microsoft Entra roles** →
   **Assignments** → **Add assignments**.
2. Role **Security Administrator**, scope **Directory**, select your working
   account → **Next**.
3. Assignment type **Eligible**. Untick **Permanently eligible**, set an end date
   6 months out. → **Assign**.
4. Repeat for: Privileged Role Administrator, Conditional Access Administrator,
   Application Administrator, Compliance Administrator, Global Administrator.

#### A3. Activate one, to prove the path works

1. **Privileged Identity Management** → **My roles** → **Microsoft Entra roles**
   → **Eligible assignments** → **Activate** next to Security Administrator.
2. Duration 1 hour. Enter a justification. **Activate**.
3. Wait for the status to reach **Activated**, then sign out and back in so your
   token picks up the role.
4. Confirm the role appears under **My roles** → **Active assignments**.

### Method B - PowerShell

```powershell
#region Context
$me       = Get-MgUser -UserId (Get-MgContext).Account
$myId     = $me.Id
$tenantScope = '/'
#endregion

# Resolve role definition IDs by display name
$roleNames = @(
    'Security Administrator'
    'Privileged Role Administrator'
    'Conditional Access Administrator'
    'Application Administrator'
    'Compliance Administrator'
    'Global Administrator'
)
$roles = Get-MgRoleManagementDirectoryRoleDefinition -All |
         Where-Object DisplayName -in $roleNames
$roles | Select-Object DisplayName, Id
```

#### Create eligible assignments

```powershell
foreach ($r in $roles) {
    $params = @{
        action           = 'adminAssign'
        justification    = 'SC-500 lab: just-in-time access instead of standing role'
        roleDefinitionId = $r.Id
        directoryScopeId = $tenantScope
        principalId      = $myId
        scheduleInfo     = @{
            startDateTime = (Get-Date).ToUniversalTime()
            expiration    = @{
                type     = 'AfterDuration'
                duration = 'P180D'
            }
        }
    }
    New-MgRoleManagementDirectoryRoleEligibilityScheduleRequest -BodyParameter $params |
        Select-Object @{n='Role';e={$r.DisplayName}}, Status
}
```

#### Inspect the activation policy

The policy is not a property of the eligibility. It is a separate object found
through a policy *assignment* that links a scope and role to a policy.

```powershell
$secAdmin = $roles | Where-Object DisplayName -eq 'Security Administrator'

$policyAssignment = Get-MgPolicyRoleManagementPolicyAssignment `
    -Filter "scopeId eq '/' and scopeType eq 'DirectoryRole' and roleDefinitionId eq '$($secAdmin.Id)'"

$rules = Get-MgPolicyRoleManagementPolicyRule -UnifiedRoleManagementPolicyId $policyAssignment.PolicyId
$rules | Select-Object Id, @{n='Type';e={$_.AdditionalProperties['@odata.type']}}
```

The rule IDs are self-describing. `Expiration_EndUser_Assignment` holds the
maximum activation duration; `Enablement_EndUser_Assignment` holds the
MFA/justification/ticket requirements.

```powershell
# Cap activation at 4 hours
Update-MgPolicyRoleManagementPolicyRule `
    -UnifiedRoleManagementPolicyId $policyAssignment.PolicyId `
    -UnifiedRoleManagementPolicyRuleId 'Expiration_EndUser_Assignment' `
    -BodyParameter @{
        '@odata.type'         = '#microsoft.graph.unifiedRoleManagementPolicyExpirationRule'
        id                    = 'Expiration_EndUser_Assignment'
        isExpirationRequired  = $true
        maximumDuration       = 'PT4H'
        target                = @{ caller = 'EndUser'; operations = @('all'); level = 'Assignment' }
    }

# Require MFA and justification on activation
Update-MgPolicyRoleManagementPolicyRule `
    -UnifiedRoleManagementPolicyId $policyAssignment.PolicyId `
    -UnifiedRoleManagementPolicyRuleId 'Enablement_EndUser_Assignment' `
    -BodyParameter @{
        '@odata.type'  = '#microsoft.graph.unifiedRoleManagementPolicyEnablementRule'
        id             = 'Enablement_EndUser_Assignment'
        enabledRules   = @('MultiFactorAuthentication', 'Justification')
        target         = @{ caller = 'EndUser'; operations = @('all'); level = 'Assignment' }
    }
```

#### Activate

```powershell
$eligible = Get-MgRoleManagementDirectoryRoleEligibilitySchedule `
    -Filter "principalId eq '$myId'" -ExpandProperty RoleDefinition -All

$target = $eligible | Where-Object { $_.RoleDefinition.DisplayName -eq 'Security Administrator' }

$activation = @{
    action           = 'selfActivate'
    principalId      = $target.PrincipalId
    roleDefinitionId = $target.RoleDefinitionId
    directoryScopeId = $target.DirectoryScopeId
    justification    = 'SC-500 lab session'
    scheduleInfo     = @{
        startDateTime = (Get-Date).ToUniversalTime()
        expiration    = @{ type = 'AfterDuration'; duration = 'PT1H' }
    }
}
New-MgRoleManagementDirectoryRoleAssignmentScheduleRequest -BodyParameter $activation |
    Select-Object Status, CompletedDateTime
```

#### Deactivate

```powershell
New-MgRoleManagementDirectoryRoleAssignmentScheduleRequest -BodyParameter @{
    action           = 'selfDeactivate'
    principalId      = $target.PrincipalId
    roleDefinitionId = $target.RoleDefinitionId
    directoryScopeId = $target.DirectoryScopeId
}
```

Save these two blocks. You will run them at the start and end of every remaining
lab in this guide.

## Part 2 - Azure resource roles

Different authorization system, different API, same PIM concept. Being Global
Administrator does nothing here.

### Method A - Portal

1. **Privileged Identity Management** → **Azure resources** → select your
   subscription → **Assignments** → **Add assignments**.
2. Role **Contributor**, member your account, **Next**.
3. Assignment type **Eligible**, 6-month expiry. **Assign**.
4. Repeat for **User Access Administrator** and **Key Vault Administrator**.
5. **Settings** → **Contributor** → **Edit** → activation maximum 4 hours,
   require MFA, require justification. **Update**.

### Method B - PowerShell

```powershell
$SubId  = (Get-AzContext).Subscription.Id
$Scope  = "/subscriptions/$SubId"
$myAzId = (Get-AzADUser -SignedIn).Id

$roleDef = Get-AzRoleDefinition -Name 'Contributor'

New-AzRoleEligibilityScheduleRequest `
    -Name (New-Guid).Guid `
    -Scope $Scope `
    -PrincipalId $myAzId `
    -RoleDefinitionId "$Scope/providers/Microsoft.Authorization/roleDefinitions/$($roleDef.Id)" `
    -RequestType AdminAssign `
    -ScheduleInfoStartDateTime (Get-Date).ToUniversalTime().ToString('o') `
    -ExpirationType AfterDuration `
    -ExpirationDuration 'P180D' `
    -Justification 'SC-500 lab just-in-time access'
```

Activate:

```powershell
New-AzRoleAssignmentScheduleRequest `
    -Name (New-Guid).Guid `
    -Scope $Scope `
    -PrincipalId $myAzId `
    -RoleDefinitionId "$Scope/providers/Microsoft.Authorization/roleDefinitions/$($roleDef.Id)" `
    -RequestType SelfActivate `
    -ScheduleInfoStartDateTime (Get-Date).ToUniversalTime().ToString('o') `
    -ExpirationType AfterDuration `
    -ExpirationDuration 'PT4H' `
    -Justification 'SC-500 lab session'
```

## Part 3 - Remove standing access

**Only after Parts 1 and 2 activated successfully at least once.**

### Method A - Portal

1. **Entra admin center** → **Roles & admins** → **Global Administrator** →
   find your working account → **Remove assignment**.
2. **Subscriptions** → your subscription → **Access control (IAM)** → **Role
   assignments** → remove the permanent Owner/Contributor assignment on your
   working account.
3. If you enabled **Access management for Azure resources** in
   [00-00](../../content/00-lab-safety/00-00-module-overview.md), toggle it back
   to **No**.

### Method B - PowerShell

```powershell
# Entra: list your PERMANENT (not activated) directory role assignments
Get-MgRoleManagementDirectoryRoleAssignment -Filter "principalId eq '$myId'" -ExpandProperty RoleDefinition |
    Select-Object Id, @{n='Role';e={$_.RoleDefinition.DisplayName}}

# Remove the standing one, by Id, after you have read the list above
# Remove-MgRoleManagementDirectoryRoleAssignment -UnifiedRoleAssignmentId '<id>'

# Azure: standing assignments at subscription scope
Get-AzRoleAssignment -ObjectId $myAzId -Scope $Scope |
    Where-Object { $_.Scope -eq $Scope } |
    Select-Object RoleDefinitionName, Scope, RoleAssignmentId

# Remove-AzRoleAssignment -ObjectId $myAzId -RoleDefinitionName 'Owner' -Scope $Scope
```

The removal lines are commented deliberately. Read the output, confirm the
emergency accounts still hold Global Administrator, then uncomment.

## Validation

```powershell
# You should have ZERO permanent directory role assignments and several eligible ones
Get-MgRoleManagementDirectoryRoleAssignment -Filter "principalId eq '$myId'" |
    Measure-Object | Select-Object -ExpandProperty Count      # expect 0

Get-MgRoleManagementDirectoryRoleEligibilitySchedule -Filter "principalId eq '$myId'" `
    -ExpandProperty RoleDefinition -All |
    Select-Object @{n='Eligible';e={$_.RoleDefinition.DisplayName}}, EndDateTime

# Break-glass accounts still hold it permanently
Get-MgRoleManagementDirectoryRoleAssignment -ExpandProperty Principal, RoleDefinition -All |
    Where-Object { $_.RoleDefinition.DisplayName -eq 'Global Administrator' } |
    Select-Object @{n='Who';e={$_.Principal.AdditionalProperties['userPrincipalName']}}
```

The last query is the one that matters. If it returns only your emergency
accounts, you did this correctly. If it returns nothing, stop and recover before
doing anything else.

### Portal validation

**Privileged Identity Management** → **Microsoft Entra roles** → **Audit
history**. Your activation and deactivation from Part 1 are there with the
justification you typed. This is the log you will query in module 04-04 — look at
it now so you know what normal looks like.

## What just happened?

- **Eligible is not active.** An eligible assignment grants nothing until it is activated; activation creates a time-bound assignment that ends on its own.
- **The rules live on the role.** Maximum duration, MFA and justification are role settings, so every eligible user gets the same rules.
- **Order kept you safe.** You proved activation worked before removing your standing role, so a recovery path existed at every step.
- **The audit history is evidence.** It records who activated what, when and why - the log you query again in 04-04.

## Limitations

- PIM limits how long access exists. It does not limit what the role can do while it is active, so choosing the smallest role still matters.
- Break-glass accounts sit outside PIM and Conditional Access on purpose. They need strong credentials, separate storage and their own monitoring.
- PIM needs Microsoft Entra ID P2 or Microsoft Entra ID Governance for the users who use it.

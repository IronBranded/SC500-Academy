# Lab 01-01 - Secure Access with Microsoft Entra ID

**Objective:** Secure access to resources by using Microsoft Entra ID
**Estimated cost:** $0 - Entra ID P2 comes with the E5 tenant; the managed identity
objects created here are free and no billable Azure resource is deployed.
**Licensing required:** Microsoft Entra ID P2
**Time:** ~150 minutes. Parts are independent; stop at any part boundary.

> Complete **Module 0** before running this lab. Activate your roles through PIM;
> do not run labs with standing Global Administrator.
>
> **This is the first lab that can lock you out of your own tenant.** Part 1 creates
> a Conditional Access policy. Do not skip step 1.1.

- Both emergency access accounts exist, hold permanent Global Administrator, and

  - Conditional Access Administrator (Part 1)
  - Authentication Policy Administrator (Part 2)

  - Privileged Role Administrator (Part 4.1)
  - Global Administrator (Part 4.2 only - activate late, deactivate immediately)
- One non-privileged test user, e.g. `sc500-01-01-testuser@<tenant>.onmicrosoft.com`.
- The Automation account `aa-sc500-brake` from [00-01](../00-lab-safety/00-01-lab.md),
  for Part 5.

## Part 1 - Conditional Access

### 1.1 Prove your recovery path first

Non-negotiable. Do this before creating any policy.

1. In a private browser window, sign in as `break-glass-01`. Confirm it works.
2. Sign out. Do not use this account again during the lab.
3. Confirm security defaults are **off**: **Entra admin center** → **Entra ID** →
   **Overview** → **Properties** → **Manage security defaults**. Conditional
   Access and security defaults cannot both be on.

```powershell
$bgUpns = @(
    'break-glass-01@<tenant>.onmicrosoft.com'
    'break-glass-02@<tenant>.onmicrosoft.com'
)
$bgIds = $bgUpns | ForEach-Object { (Get-MgUser -UserId $_).Id }
$bgIds     # must return two GUIDs before you continue
```

### Method A - Portal

#### 1.2 Create the policy in report-only

1. **Entra admin center** → **Entra ID** → **Conditional Access** → **Policies** →
   **New policy**. Name it `sc500-01-01-require-strong-auth-admins`.
2. **Users** → **Include** → **Directory roles** → select **Global Administrator**,
   **Security Administrator**, **Privileged Role Administrator**.
3. **Users** → **Exclude** → **Users and groups** → both emergency access accounts.
4. **Target resources** → **Resources** → **All resources**.
5. **Grant** → **Grant access** → **Require authentication strength** →
   **Phishing-resistant MFA**.
6. **Enable policy** → **Report-only** → **Create**.

Note what you just did in step 5: you did not select "Require multifactor
authentication." That control accepts SMS. The strength does not.

#### 1.3 Evaluate before enforcing

1. **Conditional Access** → **What If**. Set the user to your working account, the
   resource to **Windows Azure Service Management API**, and run the evaluation.
2. Read the result: your policy should appear under policies that *would* apply.
3. Re-run with `break-glass-01` as the user. It must appear as **not applied** -
   that is your exclusion working.
4. Sign in normally, then check **Entra ID** → **Sign-in logs** → your sign-in →
   **Conditional Access** tab. The policy shows a `Report-only` result.

> What If does not evaluate service dependencies. A clean result here is evidence,
> not proof.

#### 1.4 Enforce

Only after 1.3 shows what you expect: edit the policy, set **Enable policy** to
**On**, **Save**. Sign out and back in to confirm the prompt you expect, in a
private window, using your working account - never the break-glass account.

### Method B - PowerShell

```powershell
# Resolve directory role template IDs by display name rather than hardcoding GUIDs
$roleNames = 'Global Administrator','Security Administrator','Privileged Role Administrator'
$roleIds = Get-MgDirectoryRoleTemplate -All |
    Where-Object DisplayName -in $roleNames |
    Select-Object -ExpandProperty Id

# Resolve the built-in authentication strength the same way
$strength = Get-MgPolicyAuthenticationStrengthPolicy -All |
    Where-Object DisplayName -eq 'Phishing-resistant MFA'

$policy = @{
    displayName = 'sc500-01-01-require-strong-auth-admins'
    state       = 'enabledForReportingButNotEnforced'   # report-only
    conditions  = @{
        users          = @{ includeRoles = @($roleIds); excludeUsers = @($bgIds) }
        applications   = @{ includeApplications = @('All') }
        clientAppTypes = @('all')
    }
    grantControls = @{
        operator               = 'OR'
        builtInControls        = @()
        authenticationStrength = @{ id = $strength.Id }
    }
}

$created = New-MgIdentityConditionalAccessPolicy -BodyParameter $policy
$created | Select-Object Id, DisplayName, State
```

Enable it after evaluating:

```powershell
Update-MgIdentityConditionalAccessPolicy -ConditionalAccessPolicyId $created.Id `
                                         -State 'enabled'
```

> `state` accepts `enabled`, `disabled`, and `enabledForReportingButNotEnforced`.
> The third is report-only. There is no separate report-only flag.

## Part 2 - Authentication methods

### Method A - Portal

1. Create a group `sc500-01-01-strongauth` and add the test user.
2. **Entra ID** → **Authentication methods** → **Policies**.
3. Open **Temporary Access Pass** → **Enable** → target the group → **Configure**
   tab → one-time use **No**, default lifetime 60 minutes → **Save**.
4. Open **Passkey (FIDO2)** → **Enable** → target the group → **Save**.
5. Check the **Migration** status banner. If it does not read *Migration Complete*,
   finish the migration - method management in the legacy MFA and SSPR policies has
   not functioned since 30 September 2025 and a half-migrated tenant produces
   confusing results.
6. Issue a Temporary Access Pass to the test user: **Users** → the test user →
   **Authentication methods** → **Add authentication method** → **Temporary Access
   Pass**. Note the value; it is shown once.

### Method B - PowerShell

```powershell
$grp = New-MgGroup -DisplayName 'sc500-01-01-strongauth' `
                   -MailEnabled:$false -SecurityEnabled:$true `
                   -MailNickname 'sc50001013a'

# Inspect the whole policy before changing it
Get-MgPolicyAuthenticationMethodPolicy |
    Select-Object -ExpandProperty AuthenticationMethodConfigurations |
    Select-Object Id, State

$tap = @{
    '@odata.type'            = '#microsoft.graph.temporaryAccessPassAuthenticationMethodConfiguration'
    id                       = 'TemporaryAccessPass'
    state                    = 'enabled'
    isUsableOnce             = $false
    defaultLifetimeInMinutes = 60
    includeTargets           = @(
        @{ id = $grp.Id; targetType = 'group'; isRegistrationRequired = $false }
    )
}
Update-MgPolicyAuthenticationMethodPolicyAuthenticationMethodConfiguration `
    -AuthenticationMethodConfigurationId 'TemporaryAccessPass' -BodyParameter $tap
```

## Part 3 - Application identity, permissions, and consent

This part creates the two objects that confuse everyone, on purpose, so you can see
that they are two objects.

### Method A - Portal

1. **Entra ID** → **App registrations** → **New registration**. Name
   `sc500-01-01-app-reg`, single tenant, no redirect URI. **Register**.
2. Record the **Application (client) ID** and the **Object ID**.
3. Go to **Enterprise applications** and find the same app. Record *its* **Object
   ID**. Different value, same client ID. That is the app registration versus the
   service principal.
4. Back in the registration: **API permissions** → **Add a permission** →
   **Microsoft Graph** → **Delegated permissions** → `User.Read.All`. Add it.
5. Add a second: **Application permissions** → `User.Read.All`. Add it.
6. Both now show **Not granted**. Select **Grant admin consent for \<tenant\>** and
   confirm.
7. **Certificates & secrets** → **New client secret**, 30-day expiry. Copy the
   value now; it is not shown again.
8. Back in **Enterprise applications** → your app → **Permissions**. The delegated
   and application grants are listed separately. This blade is the object the
   consent created - the artifact you would pull in an incident.

### Method B - PowerShell

```powershell
$app = New-MgApplication -DisplayName 'sc500-01-01-app-reg' -SignInAudience 'AzureADMyOrg'
$sp  = New-MgServicePrincipal -AppId $app.AppId

# Two objects, one appId
[pscustomobject]@{
    AppRegistrationObjectId  = $app.Id
    ServicePrincipalObjectId = $sp.Id
    SharedAppId              = $app.AppId
}

# Resolve Microsoft Graph's own service principal and the permission definitions
$graphSp = Get-MgServicePrincipal -Filter "appId eq '00000003-0000-0000-c000-000000000000'"
$scope   = $graphSp.Oauth2PermissionScopes | Where-Object Value -eq 'User.Read.All'
$role    = $graphSp.AppRoles               | Where-Object Value -eq 'User.Read.All'

# Delegated grant  -> oauth2PermissionGrant
New-MgOauth2PermissionGrant -BodyParameter @{
    clientId    = $sp.Id
    consentType = 'AllPrincipals'
    resourceId  = $graphSp.Id
    scope       = 'User.Read.All'
}

# Application grant -> appRoleAssignment
New-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $sp.Id -BodyParameter @{
    principalId = $sp.Id
    resourceId  = $graphSp.Id
    appRoleId   = $role.Id
}

# Client secret
$secret = Add-MgApplicationPassword -ApplicationId $app.Id -PasswordCredential @{
    displayName = 'sc500-lab'
    endDateTime = (Get-Date).AddDays(30)
}
$secret.SecretText    # shown once
```

Now read the tenant the way an investigator would:

```powershell
# Every delegated grant in the tenant, resolved to app names
Get-MgOauth2PermissionGrant -All | ForEach-Object {
    [pscustomobject]@{
        Client      = (Get-MgServicePrincipal -ServicePrincipalId $_.ClientId).DisplayName
        ConsentType = $_.ConsentType
        Scope       = $_.Scope
    }
} | Sort-Object Client | Format-Table -AutoSize
```

`ConsentType` of `AllPrincipals` means tenant-wide. `Principal` means one user
consented for themselves.

## Part 4 - Consent settings

### 4.1 Restrict user consent (Privileged Role Administrator)

#### Method A - Portal

1. **Entra ID** → **Enterprise apps** → **Consent and permissions** → **User
   consent settings**.
2. Select **Allow user consent for apps from verified publishers, for selected
   permissions**.
3. Go to **Permission classifications** and classify at least `User.Read`,
   `openid`, `offline_access` as low impact. Without this, the middle option
   permits nothing at all.
4. While here: **Entra ID** → **Users** → **User settings** → set **Users can
   register applications** to **No**.

#### Method B - PowerShell

```powershell
Get-MgPolicyAuthorizationPolicy |
    Select-Object -ExpandProperty DefaultUserRolePermissions

# Verified publishers + permissions classified as low impact
Update-MgPolicyAuthorizationPolicy -DefaultUserRolePermissions @{
    permissionGrantPoliciesAssigned = @('ManagePermissionGrantsForSelf.microsoft-user-default-low')
}

# Remove the ability for any user to create a credential-bearing app object
Update-MgPolicyAuthorizationPolicy -DefaultUserRolePermissions @{
    allowedToCreateApps = $false
}
```

> To disable user consent entirely, assign an empty array to
> `permissionGrantPoliciesAssigned`. Do that only with 4.2 already in place.

### 4.2 Enable the admin consent workflow (Global Administrator)

Activate Global Administrator through PIM now, and deactivate it the moment this
step is done.

#### Method A - Portal

1. **Entra ID** → **Enterprise apps** → **Consent and permissions** → **Admin
   consent settings**.
2. **Users can request admin consent to apps they are unable to consent to** →
   **Yes**.
3. Add yourself as a reviewer, leave notifications on, set request expiry to 30
   days. **Save**.
4. Test it: as the test user, attempt to consent to any third-party app. You should
   get the **Approval required** screen. Submit a request, then approve it from
   **Enterprise apps** → **Admin consent requests**.

#### Method B - PowerShell

```powershell
$myId = (Get-MgUser -UserId (Get-MgContext).Account).Id

Update-MgPolicyAdminConsentRequestPolicy `
    -IsEnabled:$true `
    -NotifyReviewers:$true `
    -RemindersEnabled:$true `
    -RequestDurationInDays 30 `
    -Reviewers @(@{ query = "/users/$myId"; queryType = 'MicrosoftGraph' })

Get-MgPolicyAdminConsentRequestPolicy | Format-List
```

## Part 5 - Managed identities

No new billable resource. Part 5b reuses the Automation account from 00-01.

### 5a. User-assigned identity

#### Method A - Portal

1. **Azure portal** → **Resource groups** → **Create** → `rg-sc500-lab-01-01`, tag
   `sc500-module = 01-01`.
2. **Managed Identities** → **Create** → resource group `rg-sc500-lab-01-01`, name
   `id-sc500-01-01-1`. **Review + create**.
3. Open the identity → **Azure role assignments** → **Add role assignment** → scope
   **Resource group** `rg-sc500-lab-01-01`, role **Reader**. Save.
4. Note the **Object (principal) ID** and the **Client ID**. They are different, and
   code that requests a token for a specific user-assigned identity uses the client
   ID.

#### Method B - PowerShell

```powershell
$Location = 'canadacentral'
$rg = New-AzResourceGroup -Name 'rg-sc500-lab-01-01' -Location $Location `
                          -Tag @{ 'sc500-module' = '01-01' } -Force

$uami = New-AzUserAssignedIdentity -ResourceGroupName $rg.ResourceGroupName `
                                   -Name 'id-sc500-01-01-1' -Location $Location

New-AzRoleAssignment -ObjectId $uami.PrincipalId `
                     -RoleDefinitionName 'Reader' `
                     -Scope $rg.ResourceId

$uami | Select-Object Name, PrincipalId, ClientId, Id
```

### 5b. Prove a token is issued with no secret anywhere

The Automation account's system-assigned identity already holds Contributor
(granted in 00-01). Use it to see the mechanism rather than read about it.

1. **Automation Accounts** → `aa-sc500-brake` → **Runbooks** → **Create a runbook**,
   name `Show-ManagedIdentityToken`, type PowerShell, runtime 7.2+.
2. Paste:

   ```powershell
   Disable-AzContextAutosave -Scope Process | Out-Null
   $ctx = (Connect-AzAccount -Identity).Context
   Write-Output "Signed in as: $($ctx.Account.Id)  type: $($ctx.Account.Type)"
   Get-AzRoleAssignment -ObjectId $ctx.Account.Id |
       Select-Object RoleDefinitionName, Scope | Format-Table
   ```

3. **Save** → **Publish** → **Start**. Read the output.

There is no credential in that runbook. The account type reports as a managed
service identity, and its RBAC is exactly what you assigned in 00-01 - nothing more.
That is the whole value proposition, and the whole risk: any code running in this
Automation account inherits it.

## Validation

```powershell
# 1. The CA policy exists, is enforced, and excludes both break-glass accounts
$p = Get-MgIdentityConditionalAccessPolicy -All |
     Where-Object DisplayName -eq 'sc500-01-01-require-strong-auth-admins'
[pscustomobject]@{
    State            = $p.State
    ExcludedUsers    = $p.Conditions.Users.ExcludeUsers.Count
    StrengthRequired = $p.GrantControls.AuthenticationStrength.DisplayName
}

# 2. TAP is enabled and scoped to a group, not to all users
(Get-MgPolicyAuthenticationMethodPolicy).AuthenticationMethodConfigurations |
    Where-Object Id -eq 'TemporaryAccessPass' |
    Select-Object Id, State

# 3. Consent posture
(Get-MgPolicyAuthorizationPolicy).DefaultUserRolePermissions |
    Select-Object AllowedToCreateApps, PermissionGrantPoliciesAssigned
(Get-MgPolicyAdminConsentRequestPolicy).IsEnabled

# 4. The lab app holds exactly the two grants you created
Get-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $sp.Id |
    Select-Object AppRoleId, ResourceDisplayName

# 5. The managed identity has Reader and nothing else
Get-AzRoleAssignment -ObjectId $uami.PrincipalId |
    Select-Object RoleDefinitionName, Scope
```

### Portal validation

**Entra ID** → **Sign-in logs** → pick your own sign-in → **Conditional Access**
tab. Every policy that evaluated is listed with its result. This is the blade the
exam expects you to name when a question asks how you would confirm a policy
applied, and it is the same blade you would open first in an incident.

## Teardown

**Mandatory.** Run this before you close the session.

### 1. Resources
- [ ] `Remove-AzResourceGroup -Name rg-sc500-lab-01-01 -Force` (removes the
      user-assigned identity)
- [ ] `Get-AzResource -TagName 'sc500-module'` returns nothing tagged `01-01`

### 2. Subscription scope
- [ ] Remove the Reader assignment if it survived the identity:
      `Get-AzRoleAssignment -Scope $rg.ResourceId | Where-Object { -not $_.DisplayName }`
- [ ] No Defender plan was enabled by this lab - confirm none was turned on anyway

### 3. Directory scope
- [ ] **Disable the Conditional Access policy, verify you can still sign in, then
      delete it.** In that order.
      ```powershell
      Update-MgIdentityConditionalAccessPolicy -ConditionalAccessPolicyId $p.Id -State 'disabled'
      # sign out, sign in, confirm, only then:
      Remove-MgIdentityConditionalAccessPolicy -ConditionalAccessPolicyId $p.Id
      ```
- [ ] Revoke the consent grants created in Part 3:
      ```powershell
      Get-MgOauth2PermissionGrant -All | Where-Object ClientId -eq $sp.Id |
          ForEach-Object { Remove-MgOauth2PermissionGrant -OAuth2PermissionGrantId $_.Id }
      Get-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $sp.Id |
          ForEach-Object { Remove-MgServicePrincipalAppRoleAssignment `
              -ServicePrincipalId $sp.Id -AppRoleAssignmentId $_.Id }
      ```
- [ ] `Remove-MgApplication -ApplicationId $app.Id` (deletes the service principal
      with it)
- [ ] `Remove-MgGroup -GroupId $grp.Id`
- [ ] Delete the test user's Temporary Access Pass if still valid
- [ ] Delete the `Show-ManagedIdentityToken` runbook (keep the Automation account)

**Keep** the consent settings and the authentication methods policy changes. They
are tenant hardening, not lab debris, and later modules assume them.

### 4. Soft-deleted remains
- [ ] Deleted app registrations sit in **Entra ID** → **App registrations** →
      **Deleted applications** for 30 days. Purge `sc500-01-01-app-reg` there if you
      want the name back.
- [ ] Deleted users and groups are recoverable for 30 days.

### 5. Access
- [ ] Deactivate every PIM role activated for this lab, Global Administrator first
- [ ] Confirm no role is still active:
      `Get-MgRoleManagementDirectoryRoleAssignmentSchedule -Filter "principalId eq '$myId'"`

### 6. Verify
- [ ] `Get-MgIdentityConditionalAccessPolicy -All | Where-Object DisplayName -like 'sc500-01-01*'`
      returns nothing
- [ ] `Get-MgServicePrincipal -Filter "startswith(displayName,'sc500-01-01')"`
      returns nothing
- [ ] `Get-AzResourceGroup -Name 'rg-sc500-lab-01-01'` errors
- [ ] Cost Management shows no new daily run rate tomorrow

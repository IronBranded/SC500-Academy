# Lab 01-02 - Secrets and Keys with Azure Key Vault

**Objective:** Secure secrets and keys by using Azure Key Vault
**Estimated cost:** Low. Vault operations are fractions of a cent. **Defender for
Key Vault and Defender CSPM bill at subscription scope for as long as they are on** -
enable them in Part 5 and set both back to Free in teardown, the same session.
**Licensing required:** Azure subscription. Defender plans as above.
**Time:** ~120 minutes.

> Complete **Module 0** before running this lab. Activate your roles through PIM;
> do not run labs with standing Global Administrator.
>
> **Purge protection stays OFF in this lab.** It cannot be disabled once enabled,
> and turning it on here would reserve the vault name for up to 90 days with no
> override. See [00-03](../../content/00-lab-safety/00-03-teardown-checklist-template.md).

## Prerequisites

- PIM activation for this lab: **Contributor** and **User Access Administrator** at
  subscription scope (or **Owner**), plus **Key Vault Administrator** if you scoped
  it separately in [00-02](../00-lab-safety/00-02-lab.md).
- One non-privileged test user or the app registration from
  [01-01](./01-01-lab.md), to prove a role boundary in Part 2.
- Modules: `Az.KeyVault`, `Az.Resources`, `Az.Security`.
- Your current public IPv4 address. Private ranges are rejected as IP rules.

```powershell
$Location = 'canadacentral'
$LabId    = '01-02'
$Rg       = "rg-sc500-lab-$LabId"
$Vault    = "kv-sc500-0102-$((Get-Random -Maximum 9999))"   # names are globally unique
$MyIp     = (Invoke-RestMethod 'https://api.ipify.org?format=json').ip
$MyIp
```

## Part 1 - Deploy the vault

### Method A - Portal

1. **Azure portal** → **Resource groups** → **Create** → `rg-sc500-lab-01-02`, tag
   `sc500-module = 01-02`.
2. **Key vaults** → **Create**. Resource group as above, a globally unique name,
   region consistent with your other labs, pricing tier **Standard**.
3. **Recovery** tab: soft-delete retention **7** days. Leave **purge protection**
   disabled.
4. **Access configuration** tab: confirm **Azure role-based access control** is
   selected. On a current API version this is already the default for new vaults;
   confirm rather than assume, because existing vaults keep whatever they had.
5. **Networking** tab: leave public access enabled for now. Part 4 tightens it.
6. **Review + create** → **Create**.

> Diagnostic settings are deliberately not configured here. The Log Analytics
> workspace `law-sc500` is created in 04-02; this vault's `AuditEvent` log is wired
> to it in 04-03. Note the gap - until then, there is no data-plane history for
> this vault beyond what Defender for Key Vault surfaces.

### Method B - PowerShell

```powershell
New-AzResourceGroup -Name $Rg -Location $Location `
                    -Tag @{ 'sc500-module' = $LabId } -Force

$kv = New-AzKeyVault -Name $Vault `
                     -ResourceGroupName $Rg `
                     -Location $Location `
                     -Sku 'Standard' `
                     -EnableRbacAuthorization `
                     -SoftDeleteRetentionInDays 7

$kv | Format-List VaultName, VaultUri, EnableRbacAuthorization,
                  EnableSoftDelete, SoftDeleteRetentionInDays, EnablePurgeProtection
```

Read that output. `EnableSoftDelete` is `True` and there is no parameter to make it
`False` - soft delete is not optional. `EnablePurgeProtection` is empty, which is
what you want here and the opposite of what you want in production.

## Part 2 - Configure access

### 2.1 Prove the role boundary

The point of this part is not to grant yourself access. It is to see that
**Key Vault Reader and Key Vault Secrets User are different answers.**

#### Method A - Portal

1. Vault → **Access control (IAM)** → **Add role assignment**.
2. Role **Key Vault Secrets Officer**, member: yourself. Scope: this vault. Save.
3. Add a second assignment: role **Key Vault Reader**, member: your test user or the
   `sc500-01-01-app-reg` service principal. Save.
4. **Access control (IAM)** → **Check access** → select the test principal. It can
   list secrets. It cannot read a value.

#### Method B - PowerShell

```powershell
$me = (Get-AzContext).Account.Id

New-AzRoleAssignment -SignInName $me `
                     -RoleDefinitionName 'Key Vault Secrets Officer' `
                     -Scope $kv.ResourceId

# The application-shaped assignment: read values, nothing else
$sp = Get-AzADServicePrincipal -DisplayName 'sc500-01-01-app-reg'
New-AzRoleAssignment -ObjectId $sp.Id `
                     -RoleDefinitionName 'Key Vault Reader' `
                     -Scope $kv.ResourceId

Get-AzRoleAssignment -Scope $kv.ResourceId |
    Select-Object DisplayName, RoleDefinitionName, Scope | Format-Table -AutoSize
```

### 2.2 Scope an assignment to one secret

Object-level scope is supported and almost nobody uses it. Do it once so you know it
exists when a question asks for the least-privileged answer.

```powershell
# Create the secret first (Part 3 covers the object types properly)
Set-AzKeyVaultSecret -VaultName $Vault -Name 'db-conn' `
    -SecretValue (ConvertTo-SecureString 'Server=lab;Password=notreal' -AsPlainText -Force) | Out-Null

$secretScope = "$($kv.ResourceId)/secrets/db-conn"

New-AzRoleAssignment -ObjectId $sp.Id `
                     -RoleDefinitionName 'Key Vault Secrets User' `
                     -Scope $secretScope

Get-AzRoleAssignment -ObjectId $sp.Id | Select-Object RoleDefinitionName, Scope
```

The service principal can now read `db-conn` and no other secret in the vault.

### 2.3 See the other model, without adopting it

Do not switch this vault. Instead, read the property that decides everything:

```powershell
(Get-AzKeyVault -VaultName $Vault).EnableRbacAuthorization
```

If this returned `False`, access policies would govern the data plane and every RBAC
assignment above would be inert. That single boolean is the first thing to check
whenever Key Vault permissions "do not work."

## Part 3 - Keys, secrets, and certificates

### Method A - Portal

1. Vault → **Objects** → **Secrets** → **Generate/Import**. Name `api-key`, a value,
   set an **expiration date** one month out. Create.
2. Open `api-key` → **New Version** with a different value. Both versions are listed;
   the current one is at the top.
3. **Keys** → **Generate/Import**. Name `cmk-demo`, type RSA, size 2048. Create.
   Open it → **Rotation policy** → set expiry and an automatic rotation interval.
4. **Certificates** → **Generate/Import**. Name `tls-lab`, method **Generate**,
   issuer **Self**, subject `CN=sc500.lab`, validity 1 month. Create. Once it shows
   as enabled, note that **Keys** and **Secrets** now each contain an object named
   `tls-lab` - one certificate created three addressable things.

### Method B - PowerShell

```powershell
# Secret, with an expiry, then a second version
Set-AzKeyVaultSecret -VaultName $Vault -Name 'api-key' `
    -SecretValue (ConvertTo-SecureString 'v1-value' -AsPlainText -Force) `
    -Expires (Get-Date).AddMonths(1)

Set-AzKeyVaultSecret -VaultName $Vault -Name 'api-key' `
    -SecretValue (ConvertTo-SecureString 'v2-value' -AsPlainText -Force)

Get-AzKeyVaultSecret -VaultName $Vault -Name 'api-key' -IncludeVersions |
    Select-Object Version, Created, Expires

# Unversioned read returns the current version - this is what makes rotation transparent
Get-AzKeyVaultSecret -VaultName $Vault -Name 'api-key' -AsPlainText

# Key: the private material never leaves the vault
Add-AzKeyVaultKey -VaultName $Vault -Name 'cmk-demo' -Destination 'Software' -Size 2048

# Certificate: one command, three objects
$policy = New-AzKeyVaultCertificatePolicy -SecretContentType 'application/x-pkcs12' `
                                          -SubjectName 'CN=sc500.lab' `
                                          -IssuerName 'Self' `
                                          -ValidityInMonths 1 `
                                          -ReuseKeyOnRenewal
Add-AzKeyVaultCertificate -VaultName $Vault -Name 'tls-lab' -CertificatePolicy $policy

Start-Sleep 20
Get-AzKeyVaultKey    -VaultName $Vault | Select-Object Name
Get-AzKeyVaultSecret -VaultName $Vault | Select-Object Name
```

> `-AsPlainText` on `Get-AzKeyVaultSecret` is convenient and it puts the secret in
> your shell history and console buffer. In anything but a lab, bind the
> `SecureString` directly.

## Part 4 - Firewall settings

**Order matters.** Add your allow rule first, then change the default action. The
reverse order locks you out of the data plane for as long as it takes you to notice.

### Method A - Portal

1. Vault → **Networking** → **Firewalls and virtual networks**.
2. **Allow access from**: *Allow public access from specific virtual networks and IP
   addresses*.
3. Under **Firewall**, add your public IPv4 address.
4. Under **Exception**, tick **Allow trusted Microsoft services to bypass this
   firewall**. Save.
5. Try reading a secret. It works - you allowed your address.
6. Now remove your IP rule and save. Try again. The data plane fails; the
   **Overview** blade and the vault's tags still load, because that is the control
   plane. Put your IP back.
7. Optional, if you have a virtual network: enable the `Microsoft.KeyVault` service
   endpoint on a subnet, then add that subnet as a virtual network rule.

### Method B - PowerShell

```powershell
# 1. Allow rule FIRST
Add-AzKeyVaultNetworkRule -VaultName $Vault -IpAddressRange "$MyIp/32"

# 2. Then flip the default to Deny, keeping the trusted-services bypass
Update-AzKeyVaultNetworkRuleSet -VaultName $Vault `
                                -DefaultAction Deny `
                                -Bypass AzureServices

(Get-AzKeyVault -VaultName $Vault).NetworkAcls |
    Format-List DefaultAction, Bypass, IpAddressRanges, VirtualNetworkResourceIds

# 3. Data plane still works from your address
Get-AzKeyVaultSecret -VaultName $Vault -Name 'api-key' -AsPlainText

# 4. Remove your rule and watch the data plane fail while the control plane does not
Remove-AzKeyVaultNetworkRule -VaultName $Vault -IpAddressRange "$MyIp/32"
Get-AzKeyVault -VaultName $Vault | Select-Object VaultName, Location   # control plane: OK
Get-AzKeyVaultSecret -VaultName $Vault -Name 'api-key'                 # data plane: forbidden

# 5. Restore
Add-AzKeyVaultNetworkRule -VaultName $Vault -IpAddressRange "$MyIp/32"
```

Step 4 is the whole point of this part. Write down which command failed and which
did not, and why.

> Private-IP ranges are rejected as IP rules. If you are behind NAT, the address you
> need is the public egress address, which is what `api.ipify.org` returned.
> Disabling public access entirely, with a private endpoint and private DNS, is built
> in module **02-04** where the virtual network already exists.

## Part 5 - Defender plans

**Cost gate.** Both plans below bill at subscription scope. Enable, observe,
disable - in this session. The teardown section turns them off.

### Method A - Portal

1. **Defender for Cloud** → **Environment settings** → your subscription →
   **Defender plans**.
2. Toggle **Key Vault** to **On**. Save.
3. Toggle **Defender CSPM** to **On**. Save. Note that foundational CSPM is free and
   does *not* include secret scanning; that capability is why you are turning on the
   paid plan.
4. **Defender for Cloud** → **Security alerts** → **Sample alerts**. Select your
   subscription and the Key Vault plan, create the samples. Open one and read its
   structure: resource, principal, source address, and the detection logic
   description. This is the alert shape you would triage.
5. **Defender for Cloud** → **Recommendations**, filter on Key Vault. Confirm the
   vault appears and what it is being assessed against.
6. Secret scanning: **Defender for Cloud** → **Inventory** / **Recommendations**,
   search for secrets findings. **Expect nothing.** Machine scanning needs machines
   and this subscription has none. Record the empty result deliberately - an empty
   scan surface is not a clean scan.

### Method B - PowerShell

```powershell
# Record current state so teardown can restore it exactly
Get-AzSecurityPricing | Where-Object Name -in 'KeyVaults','CloudPosture' |
    Select-Object Name, PricingTier

Set-AzSecurityPricing -Name 'KeyVaults'    -PricingTier 'Standard'
Set-AzSecurityPricing -Name 'CloudPosture' -PricingTier 'Standard'

Get-AzSecurityPricing | Where-Object PricingTier -eq 'Standard' |
    Select-Object Name, PricingTier, SubPlan
```

Sample alerts are portal-driven; there is no first-party cmdlet for them.

## Validation

```powershell
# 1. Vault posture
Get-AzKeyVault -VaultName $Vault |
    Format-List VaultName, EnableRbacAuthorization, EnableSoftDelete,
                SoftDeleteRetentionInDays, EnablePurgeProtection

# 2. Network rules: default Deny, exactly one IP rule, trusted services bypass
(Get-AzKeyVault -VaultName $Vault).NetworkAcls |
    Format-List DefaultAction, Bypass, IpAddressRanges

# 3. Least privilege actually scoped to one secret
Get-AzRoleAssignment -Scope $kv.ResourceId -ExpandPrincipalGroups:$false |
    Select-Object DisplayName, RoleDefinitionName, Scope | Format-Table -AutoSize

# 4. Objects exist and are versioned
Get-AzKeyVaultSecret -VaultName $Vault | Select-Object Name, Enabled, Expires
Get-AzKeyVaultKey    -VaultName $Vault | Select-Object Name, Enabled

# 5. Defender plans are on - and remember they are billing right now
Get-AzSecurityPricing | Where-Object Name -in 'KeyVaults','CloudPosture' |
    Select-Object Name, PricingTier
```

### Portal validation

**Defender for Cloud** → **Security alerts**, filtered to the vault. This is the
blade an exam question means when it asks how you would detect anomalous access to a
key vault - not the vault's own blades, which show configuration, not behaviour.

      ```powershell
      Get-AzKeyVault -InRemovedState | Where-Object VaultName -like 'kv-sc500-0102*' |
          Format-Table VaultName, Location, DeletionDate, PurgeProtectionEnabled

      Remove-AzKeyVault -VaultName $Vault -Location $Location -InRemovedState -Force
      ```
- [ ] Deleted secrets, keys, and certificates go with the vault. Purging the vault
      purges them.

- [ ] Confirm nothing is still active before you close the session

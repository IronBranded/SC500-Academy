# Lab 02-01 - Storage Account Security

**Objective:** Implement security for storage accounts
**Estimated cost:** Low. A Standard_LRS account holding a few kilobytes costs
pennies. **Defender for Storage is billed per storage account per month** - Part 5
enables it at *resource* scope for one account, and teardown disables it.
**Licensing required:** Azure subscription; Defender for Storage plan for Part 5.
**Time:** ~150 minutes.

> Complete **Module 0** before running this lab. Activate your roles through PIM;
> do not run labs with standing Global Administrator.
>
> **Order matters in Part 2.** Assign yourself the data role *before* disabling
> shared key, or you will lock yourself out of your own container in the portal.

## Prerequisites

- PIM activation: **Contributor** and **User Access Administrator** at subscription
  scope, or Owner. Data-plane role assignments need
  `Microsoft.Authorization/roleAssignments/write`.
- The `sc500-01-01-app-reg` service principal from
  [01-01](../01-identity-access-governance/01-01-lab.md), as a second principal.
- Modules: `Az.Storage`, `Az.Security`, `Az.Resources`.
- The **EICAR anti-malware test file** for Part 5. Download it from
  <https://www.eicar.org/download-anti-malware-testfile/> - it is a harmless standard
  test string that every antivirus engine is built to detect, not malware.

```powershell
$Location = 'canadacentral'
$LabId    = '02-01'
$Rg       = "rg-sc500-lab-$LabId"
$Sa       = "stsc500$((Get-Random -Maximum 99999))"
$SubId    = (Get-AzContext).Subscription.Id
$MyIp     = (Invoke-RestMethod 'https://api.ipify.org?format=json').ip

New-AzResourceGroup -Name $Rg -Location $Location -Tag @{ 'sc500-module' = $LabId } -Force
```

## Part 1 - Deploy a hardened account

### Method A - Portal

1. **Storage accounts** → **Create**. Resource group `rg-sc500-lab-02-01`, a unique
   name, **Standard**, redundancy **LRS**.
2. **Advanced** tab:
   - Require secure transfer: **enabled**
   - Allow enabling anonymous access on individual containers: **unticked**
   - Enable storage account key access: **ticked for now** (Part 2 turns it off in
     the right order)
   - Minimum TLS version: **1.2**
   - Infrastructure encryption: read the note - **this is creation-time only.** Leave
     it off here and remember you cannot add it later.
3. **Networking** tab: public access from all networks for now. Part 3 tightens it.
4. **Data protection** tab: enable **blob soft delete** (7 days) and **versioning**.
5. **Review + create**.

### Method B - PowerShell

```powershell
$sa = New-AzStorageAccount -ResourceGroupName $Rg -Name $Sa -Location $Location `
                           -SkuName Standard_LRS -Kind StorageV2 `
                           -EnableHttpsTrafficOnly $true `
                           -MinimumTlsVersion TLS1_2 `
                           -AllowBlobPublicAccess $false `
                           -AllowSharedKeyAccess $true `
                           -Tag @{ 'sc500-module' = $LabId }

Enable-AzStorageBlobDeleteRetentionPolicy -ResourceGroupName $Rg -StorageAccountName $Sa -RetentionDays 7
Update-AzStorageBlobServiceProperty -ResourceGroupName $Rg -StorageAccountName $Sa -IsVersioningEnabled $true

$sa | Format-List StorageAccountName, EnableHttpsTrafficOnly, MinimumTlsVersion,
                  AllowBlobPublicAccess, AllowSharedKeyAccess
```

### 1.3 Prove the public-access kill switch

```powershell
$ctxKey = New-AzStorageContext -StorageAccountName $Sa -UseConnectedAccount
New-AzStorageContainer -Name 'lab' -Context $ctxKey

# Attempt to make it publicly readable. With AllowBlobPublicAccess = false this fails.
Set-AzStorageContainerAcl -Name 'lab' -Permission Blob -Context $ctxKey
```

The account-level switch overrides the container setting. That is the control you
want in an exam answer about preventing anonymous access "on any container."

## Part 2 - Authorization: four systems, then two

### 2.1 Show that Contributor owns the data plane

```powershell
# Control-plane role, data-plane outcome
Get-AzStorageAccountKey -ResourceGroupName $Rg -Name $Sa | Select-Object KeyName
```

`listKeys` is a control-plane operation and it just handed you both account keys.
Anyone with Contributor has full data access while shared key is enabled.

### 2.2 Assign data roles FIRST

#### Method A - Portal

Storage account → **Access control (IAM)** → **Add role assignment** →
**Storage Blob Data Contributor** → yourself. Then add **Storage Blob Data Reader**
for the `sc500-01-01-app-reg` service principal.

#### Method B - PowerShell

```powershell
$me = (Get-AzContext).Account.Id
New-AzRoleAssignment -SignInName $me `
                     -RoleDefinitionName 'Storage Blob Data Contributor' -Scope $sa.Id

$sp = Get-AzADServicePrincipal -DisplayName 'sc500-01-01-app-reg'
New-AzRoleAssignment -ObjectId $sp.Id `
                     -RoleDefinitionName 'Storage Blob Data Reader' -Scope $sa.Id

Start-Sleep 60   # role assignments take a minute to propagate to the data plane
```

### 2.3 Stored access policy and a revocable service SAS

```powershell
"hello sc500" | Set-Content .\sample.txt
Set-AzStorageBlobContent -File .\sample.txt -Container 'lab' -Blob 'sample.txt' -Context $ctxKey

# A policy on the container, then a SAS that references it by name
New-AzStorageContainerStoredAccessPolicy -Container 'lab' -Policy 'sc500-readonly' `
    -Permission rl -ExpiryTime (Get-Date).AddDays(7) -Context $ctxKey

$sasWithPolicy = New-AzStorageContainerSASToken -Name 'lab' -Policy 'sc500-readonly' `
                                                -Context $ctxKey -FullUri
$sasWithPolicy

# A standalone SAS with the permissions baked into the signature
$sasStandalone = New-AzStorageContainerSASToken -Name 'lab' -Permission rl `
                                                -ExpiryTime (Get-Date).AddDays(7) `
                                                -Context $ctxKey -FullUri
```

Open both URLs in a private browser window. Both work. Now revoke one:

```powershell
Remove-AzStorageContainerStoredAccessPolicy -Container 'lab' -Policy 'sc500-readonly' -Context $ctxKey
```

Refresh both. The policy-bound SAS is dead. **The standalone one still works**, and
the only way to kill it is rotating the account key - which would break every other
consumer on the account. Write that down; it is the most common real finding in a
storage review.

### 2.4 User delegation SAS

```powershell
$ctxOAuth = New-AzStorageContext -StorageAccountName $Sa -UseConnectedAccount

$udSas = New-AzStorageBlobSASToken -Container 'lab' -Blob 'sample.txt' `
                                   -Permission r -ExpiryTime (Get-Date).AddHours(1) `
                                   -Context $ctxOAuth -FullUri
$udSas
```

A context built with `-UseConnectedAccount` produces a **user delegation SAS**,
signed with a key Entra issued on your behalf. It cannot outlive the delegation key,
cannot exceed your own RBAC, and is attributable to you.

### 2.5 Disable shared key

```powershell
Set-AzStorageAccount -ResourceGroupName $Rg -Name $Sa -AllowSharedKeyAccess $false
Start-Sleep 30

Get-AzStorageBlob -Container 'lab' -Context $ctxOAuth      # Entra: still works
```

Now re-test every credential from 2.3 and 2.4. The standalone service SAS is dead
too - it was signed with the account key. The user delegation SAS survives. One
switch, and the four authorization systems became two.

## Part 3 - Firewall rules

### Method A - Portal

1. Storage account → **Networking** → **Firewalls and virtual networks**.
2. **Enabled from selected virtual networks and IP addresses**.
3. Add your public IPv4 address under **Firewall**.
4. Under **Exceptions**, leave *Allow Azure services on the trusted services list*
   **unticked** for now. Save.
5. Browse to **Containers**. Data blades work from your allowed address; try it from
   a phone on cellular and they do not.
6. Now add a **resource instance** rule instead: **Networking** → **Resource
   instances** → add a specific resource. Compare the two exceptions - one names a
   resource, the other admits a service class.

### Method B - PowerShell

```powershell
Add-AzStorageAccountNetworkRule -ResourceGroupName $Rg -Name $Sa -IPAddressOrRange $MyIp

Update-AzStorageAccountNetworkRuleSet -ResourceGroupName $Rg -Name $Sa `
                                      -DefaultAction Deny -Bypass None

(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Sa).NetworkRuleSet |
    Format-List DefaultAction, Bypass, IpRules, VirtualNetworkRules, ResourceAccessRules

Get-AzStorageBlob -Container 'lab' -Context $ctxOAuth   # works: your IP is allowed

Remove-AzStorageAccountNetworkRule -ResourceGroupName $Rg -Name $Sa -IPAddressOrRange $MyIp
Get-AzStorageBlob -Container 'lab' -Context $ctxOAuth   # 403: allowed network is a gate, not a grant

Add-AzStorageAccountNetworkRule -ResourceGroupName $Rg -Name $Sa -IPAddressOrRange $MyIp
```

Note what did **not** break while the data plane was blocked:

```powershell
Get-AzStorageAccount -ResourceGroupName $Rg -Name $Sa | Select-Object StorageAccountName, Location
```

Control plane, unaffected - exactly as with Key Vault in
[01-02](../01-identity-access-governance/01-02-lab.md).

## Part 4 - SAS expiration policy and data protection

```powershell
# Recommend (and report on) a maximum SAS lifetime. Verify the parameter name
# against your installed Az.Storage: Get-Command Set-AzStorageAccount -Syntax
Set-AzStorageAccount -ResourceGroupName $Rg -Name $Sa -SasExpirationPeriod '1.00:00:00'

Get-AzStorageAccount -ResourceGroupName $Rg -Name $Sa |
    Select-Object -ExpandProperty SasPolicy
```

This does not enforce anything - it sets the line a SAS is measured against, so
over-long SAS tokens surface as a recommendation rather than as a surprise.

In the portal, look at **Data protection** and confirm blob soft delete and
versioning from Part 1. Delete `sample.txt`, then recover it from **Show deleted
blobs**. Ransomware and a misfired script are indistinguishable at the moment they
happen; this is the control that makes both survivable.

## Part 5 - Defender for Storage

**Cost gate.** Enable at **resource** scope so only this one account is billed.

### Method A - Portal

1. Storage account → **Microsoft Defender for Cloud** → **Settings** → enable
   **Microsoft Defender for Storage** for this account.
2. Open the plan settings. Confirm:
   - **On-upload malware scanning**: On
   - **Malware scanning cap**: lower it to something small, e.g. 10 GB per month
   - **Sensitive data threat detection**: On - note it costs nothing extra and adds
     no new alert types
3. Upload the EICAR test file to the `lab` container.
4. Wait a few minutes, then check **Defender for Cloud** → **Security alerts**, and
   the blob's **index tags** for the scan result.
5. Read **Environment settings** → subscription → **Defender plans** → **Storage** →
   **Settings** to see the same options at subscription scope, and note the
   **exclusions** list - that is how production enables everywhere but two accounts.

### Method B - PowerShell

```powershell
# Subscription-scope enablement, for reference. The SubPlan name and the extension
# syntax for malware scanning move between Az.Security versions - check
# Get-Command Set-AzSecurityPricing -Syntax before scripting this in anger.
Get-AzSecurityPricing -Name 'StorageAccounts' | Format-List Name, PricingTier, SubPlan
```

Resource-scope enablement and the malware-scanning configuration are portal-driven
above for that reason.

### 5.3 Event-driven response

Do not build it here - it belongs with Logic Apps in 03-06. Read the plan's response
settings and note the shape: malware scan results publish to **Event Grid**, and a
Function or Logic App subscribes and deletes or quarantines the blob. An emailed
alert is not a response.

## Validation

```powershell
# 1. Account hardening
Get-AzStorageAccount -ResourceGroupName $Rg -Name $Sa |
    Format-List AllowSharedKeyAccess, AllowBlobPublicAccess,
                EnableHttpsTrafficOnly, MinimumTlsVersion

# 2. Firewall: Deny plus exactly one IP rule
(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Sa).NetworkRuleSet |
    Format-List DefaultAction, IpRules, Bypass

# 3. Data-plane roles, separate from control-plane roles
Get-AzRoleAssignment -Scope $sa.Id |
    Select-Object DisplayName, RoleDefinitionName | Format-Table -AutoSize

# 4. No stored access policies left behind
Get-AzStorageContainerStoredAccessPolicy -Container 'lab' -Context $ctxOAuth

# 5. Data protection
Get-AzStorageBlobServiceProperty -ResourceGroupName $Rg -StorageAccountName $Sa |
    Format-List IsVersioningEnabled, DeleteRetentionPolicy
```

### Portal validation

**Defender for Cloud** → **Security alerts**, filtered to the storage account, plus
the blob index tag written by the malware scan. Those two surfaces are what an exam
question means by "how would you confirm a malicious upload was detected" - not the
storage account's own metrics.

## Teardown

**Mandatory.** The Defender plan is the part that keeps billing.

### 1. Resources
- [ ] `Remove-AzResourceGroup -Name rg-sc500-lab-02-01 -Force`
- [ ] Delete `.\sample.txt` and the EICAR file from your working directory
- [ ] `Get-AzResource -TagName 'sc500-module'` shows nothing tagged `02-01`

### 2. Subscription scope
- [ ] **Disable Defender for Storage.** If you enabled at resource scope, turn it off
      on the account before deleting it; if you also touched subscription scope:
      ```powershell
      Set-AzSecurityPricing -Name 'StorageAccounts' -PricingTier 'Free'
      Get-AzSecurityPricing | Where-Object PricingTier -eq 'Standard'   # expect empty
      ```
- [ ] Remove the data-plane role assignments - deleting the account orphans them:
      ```powershell
      Get-AzRoleAssignment -Scope $sa.Id | Where-Object { -not $_.DisplayName }
      ```

### 3. Directory scope
- [ ] Nothing created here. The service principal belongs to 01-01.

### 4. Soft-deleted remains
- [ ] Blob soft delete and versioning retain data for 7 days inside the account. The
      account itself has no soft delete, so deleting the resource group removes
      everything. Note the asymmetry with Key Vault.

### 5. Access
- [ ] Deactivate every PIM role activated for this lab
- [ ] **Destroy every SAS URL you generated.** Clear your shell history if the
      standalone SAS from 2.3 is still in it - disabling shared key killed it, but
      the habit is the point

### 6. Verify
- [ ] `Get-AzStorageAccount -ResourceGroupName $Rg` errors
- [ ] `Get-AzSecurityPricing | Where-Object PricingTier -eq 'Standard'` is empty
- [ ] `Get-AzResourceGroup -Name rg-sc500-lab-02-01` errors
- [ ] Cost Management shows no new daily run rate tomorrow, and no line item for
      Defender for Storage next month

# Lab 02-02 - Database Security

**Objective:** Implement security for databases
**Estimated cost:** Medium. Azure SQL Database **serverless** with auto-pause costs
cents per lab session. A Log Analytics workspace ingesting a handful of audit records
is effectively free. **Defender for Databases bills per server per month** - enable it
in Part 5, disable it in teardown.
**Licensing required:** Azure subscription; Defender for Databases plan for Part 5.
**Time:** ~150 minutes.

> **Do not deploy Azure SQL Managed Instance.** It takes hours to provision, costs
> hundreds of dollars a month, and nothing in this lab needs it. Managed Instance
> auditing is covered in the module text; the exam tests that you know it audits to
> the same three destinations, not that you have run one.
>
> **Ordering trap in Part 1.** Set the Microsoft Entra admin *before* enabling
> Entra-only authentication. Reversing that is how you lock yourself out of a server
> whose only other credential you just disabled.

## Prerequisites

- PIM activation: **Contributor** and **User Access Administrator** at subscription
  scope, or Owner.
- Modules: `Az.Sql`, `Az.Security`, `Az.Monitor`, `Az.OperationalInsights`, and
  `SqlServer` for `Invoke-Sqlcmd`.

```powershell
$Location = 'canadacentral'
$LabId    = '02-02'
$Rg       = "rg-sc500-lab-$LabId"
$Server   = "sql-sc500-0202-$((Get-Random -Maximum 9999))"
$Db       = 'db-sc500-0202'
$Law      = "law-sc500-lab-$LabId"
$MyIp     = (Invoke-RestMethod 'https://api.ipify.org?format=json').ip

New-AzResourceGroup -Name $Rg -Location $Location -Tag @{ 'sc500-module' = $LabId } -Force
```

## Part 1 - Deploy, then disconnect SQL authentication

### Method A - Portal

1. **SQL databases** → **Create**. Resource group `rg-sc500-lab-02-02`, database name
   `db-sc500-0202`, **Create new** server.
2. On the server blade: authentication method **Use both SQL and Microsoft Entra
   authentication** for now. Set yourself as **Microsoft Entra admin**. Give the SQL
   admin a strong password you will discard in step 5.
3. **Compute + storage** → **Configure database** → **Serverless**, General Purpose,
   Gen5, min **0.5** vCore, max 1, **auto-pause after 1 hour**. Apply.
4. **Networking**: public endpoint, **add your client IP**. Leave *Allow Azure
   services and resources to access this server* **unchecked** - Part 2 examines it.
5. After deployment: server → **Microsoft Entra ID** → confirm the admin, then tick
   **Support only Microsoft Entra authentication for this server** and save. Read the
   warning: SQL logins, including the admin you just created, stop working.

### Method B - PowerShell

```powershell
$sqlAdminPwd = ConvertTo-SecureString (New-Guid).Guid -AsPlainText -Force
$cred = New-Object System.Management.Automation.PSCredential('sqladmin-discard', $sqlAdminPwd)

$srv = New-AzSqlServer -ResourceGroupName $Rg -ServerName $Server -Location $Location `
                       -SqlAdministratorCredentials $cred `
                       -MinimalTlsVersion '1.2' `
                       -AssignIdentity `
                       -Tags @{ 'sc500-module' = $LabId }

New-AzSqlDatabase -ResourceGroupName $Rg -ServerName $Server -DatabaseName $Db `
                  -Edition 'GeneralPurpose' -ComputeModel 'Serverless' `
                  -ComputeGeneration 'Gen5' -MinVcore 0.5 -MaxVcore 1 `
                  -AutoPauseDelayInMinutes 60

New-AzSqlServerFirewallRule -ResourceGroupName $Rg -ServerName $Server `
                            -FirewallRuleName 'my-client' `
                            -StartIpAddress $MyIp -EndIpAddress $MyIp

# 1. Entra admin FIRST
$me = Get-AzADUser -SignedIn
Set-AzSqlServerActiveDirectoryAdministrator -ResourceGroupName $Rg -ServerName $Server `
                                            -DisplayName $me.UserPrincipalName `
                                            -ObjectId $me.Id

# 2. Only then disable SQL authentication
Enable-AzSqlServerActiveDirectoryOnlyAuthentication -ResourceGroupName $Rg -ServerName $Server

Get-AzSqlServerActiveDirectoryOnlyAuthentication -ResourceGroupName $Rg -ServerName $Server
```

### 1.3 Connect with an Entra token

```powershell
# Newer Az versions return a SecureString by default. -AsPlainText may be required
# or unavailable depending on your version: Get-Command Get-AzAccessToken -Syntax
$token = (Get-AzAccessToken -ResourceUrl 'https://database.windows.net/').Token

Invoke-Sqlcmd -ServerInstance "$Server.database.windows.net" -Database $Db `
              -AccessToken $token `
              -Query "SELECT SUSER_SNAME() AS connected_as, @@VERSION AS version"
```

`connected_as` is your Entra identity. There is no password anywhere in that command,
and that connection was subject to every Conditional Access policy from 01-01. The SQL
admin login you created in Method B no longer works at all.

## Part 2 - Firewall rules

### 2.1 Look at what "Allow Azure services" actually writes

```powershell
# Do this only to read it, then remove it
New-AzSqlServerFirewallRule -ResourceGroupName $Rg -ServerName $Server `
                            -AllowAllAzureIPs

Get-AzSqlServerFirewallRule -ResourceGroupName $Rg -ServerName $Server |
    Select-Object FirewallRuleName, StartIpAddress, EndIpAddress | Format-Table -AutoSize
```

The rule is named `AllowAllWindowsAzureIps` with range `0.0.0.0` to `0.0.0.0`. That is
not "your Azure resources" - it admits any resource in any Azure subscription in any
tenant. Remove it now and remember what the toggle means when you see it in a
question or an audit:

```powershell
Remove-AzSqlServerFirewallRule -ResourceGroupName $Rg -ServerName $Server `
                               -FirewallRuleName 'AllowAllWindowsAzureIps'
```

### 2.2 Database-level rules are evaluated first

```powershell
Invoke-Sqlcmd -ServerInstance "$Server.database.windows.net" -Database $Db `
              -AccessToken $token -Query @"
EXECUTE sp_set_database_firewall_rule N'db-only-my-client', '$MyIp', '$MyIp';
SELECT * FROM sys.database_firewall_rules;
"@
```

Server rules live in `master` and cover every database; database rules narrow within
one. Now remove your server-level rule and confirm the database rule alone still lets
you in - then put the server rule back.

### 2.3 Remove the public endpoint

```powershell
Set-AzSqlServer -ResourceGroupName $Rg -ServerName $Server -PublicNetworkAccess 'Disabled'
Invoke-Sqlcmd -ServerInstance "$Server.database.windows.net" -Database $Db `
              -AccessToken $token -Query "SELECT 1"     # fails

Set-AzSqlServer -ResourceGroupName $Rg -ServerName $Server -PublicNetworkAccess 'Enabled'
```

With no private endpoint there is now no route at all. A private endpoint for SQL is
built in **02-04**, where the virtual network already exists - note here that the
connection policy matters then: `Redirect` needs ports 11000-11999 open, and a
restrictive NSG blocking them produces a failure that looks like authentication.

## Part 3 - Masking is not a boundary

```powershell
Invoke-Sqlcmd -ServerInstance "$Server.database.windows.net" -Database $Db `
              -AccessToken $token -Query @"
CREATE TABLE dbo.Customer (
    Id      int IDENTITY PRIMARY KEY,
    Name    nvarchar(64),
    NatId   char(9) MASKED WITH (FUNCTION = 'partial(0,"XXX-XX-",4)') NULL,
    Region  nvarchar(16)
);
INSERT INTO dbo.Customer (Name, NatId, Region) VALUES
 ('Alice','123456789','east'), ('Bob','987654321','west');
SELECT * FROM dbo.Customer;
"@
```

You are the admin, so you see the real values. The masking applies to unprivileged
readers. Now demonstrate why that is not a security boundary - an unprivileged user
can recover a masked value one predicate at a time:

```powershell
Invoke-Sqlcmd -ServerInstance "$Server.database.windows.net" -Database $Db `
              -AccessToken $token -Query @"
SELECT COUNT(*) AS matches FROM dbo.Customer WHERE NatId LIKE '123%';
"@
```

The value is masked in the output and fully available to the `WHERE` clause. Ten
queries recover the whole number. **Dynamic Data Masking prevents casual exposure in
an application; it does not protect data from someone who can query it.** When a
question says "protect from the database administrator," the answer is Always
Encrypted, where the keys never reach the server at all.

Add Row-Level Security, which *is* a boundary, to feel the difference:

```powershell
Invoke-Sqlcmd -ServerInstance "$Server.database.windows.net" -Database $Db `
              -AccessToken $token -Query @"
CREATE SCHEMA sec;
GO
CREATE FUNCTION sec.fn_region(@Region nvarchar(16))
    RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS ok WHERE @Region = 'east' OR IS_ROLEMEMBER('db_owner') = 1;
GO
CREATE SECURITY POLICY sec.RegionFilter
    ADD FILTER PREDICATE sec.fn_region(Region) ON dbo.Customer
    WITH (STATE = ON);
"@
```

The predicate runs inside the engine. Rows that fail it do not exist as far as the
query is concerned - no masking to defeat.

## Part 4 - Auditing

### 4.1 A workspace to audit into

```powershell
$law = New-AzOperationalInsightsWorkspace -ResourceGroupName $Rg -Name $Law `
                                          -Location $Location -Sku 'PerGB2018' `
                                          -RetentionInDays 30
```

> This is a **lab-scoped** workspace, deliberately separate from `law-sc500`, which is
> created in 04-02. Log Analytics workspaces are **soft-deleted for 14 days** and
> recreating the same name in the same resource group and region recovers the old one
> - see [00-03](../../content/00-lab-safety/00-03-teardown-checklist-template.md).

### Method A - Portal

1. SQL **server** → **Security** → **Auditing** → **Enable Azure SQL Auditing**.
2. Tick **Log Analytics**, select the workspace. Save.
3. Note the **Storage** option and its two authentication types - **Managed Identity**
   and **Storage access keys**. Do not configure it; just register that managed
   identity is the right answer and that the storage account's firewall would then need
   a resource instance rule, exactly as in 02-01.
4. Open the **database** → **Auditing**. Leave it **off**. Read the note that a
   database policy runs side by side with the server policy - two audits, two sets of
   records, two ingestion bills.

### Method B - PowerShell

```powershell
Set-AzSqlServerAudit -ResourceGroupName $Rg -ServerName $Server `
                     -LogAnalyticsTargetState Enabled `
                     -WorkspaceResourceId $law.ResourceId

Get-AzSqlServerAudit -ResourceGroupName $Rg -ServerName $Server |
    Format-List LogAnalyticsTargetState, AuditActionGroup
```

The default action groups are `BATCH_COMPLETED_GROUP`,
`SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP`, and
`FAILED_DATABASE_AUTHENTICATION_GROUP` - every statement, plus successful and failed
logins.

### 4.2 Generate and read audit records

```powershell
1..5 | ForEach-Object {
    Invoke-Sqlcmd -ServerInstance "$Server.database.windows.net" -Database $Db `
                  -AccessToken $token -Query "SELECT TOP 1 * FROM dbo.Customer"
}

Start-Sleep 300   # ingestion latency is minutes, not seconds

Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId -Query @"
SQLSecurityAuditEvents
| where TimeGenerated > ago(1h)
| project TimeGenerated, ServerPrincipalName, ClientIp, Statement, Succeeded
| take 20
"@ | Select-Object -ExpandProperty Results | Format-Table -AutoSize
```

`Statement` is the point. This log records *what was asked*, not merely that a
connection happened - which is why it is the database log worth having, and why the
4,000-character truncation matters for very long statements.

## Part 5 - Defender for Databases

**Cost gate.** The Azure SQL sub-plan bills per server per month. Enable, observe,
disable.

### Method A - Portal

1. **Defender for Cloud** → **Environment settings** → subscription → **Defender
   plans** → **Databases** → **Select types**. Note the separate sub-plans: Azure SQL
   Databases, SQL servers on machines, open-source relational databases, Azure Cosmos
   DB. Enable **Azure SQL Databases** only. Save.
2. Open the database → **Security** → **Defender for Cloud**. Confirm Advanced Threat
   Protection and vulnerability assessment are already on - enabling the plan turned
   both on automatically.
3. Select **Configure**. **If it offers you a storage account, you are on classic.**
   You should not be; express configuration needs none.
4. Run a **vulnerability assessment scan**. Review findings, then **baseline** one you
   accept. On express configuration the baseline applies **without rescanning**.
5. **Defender for Cloud** → **Security alerts** → **Sample alerts**, selecting the
   Databases plan. Read one SQL alert end to end - what triggered it, which principal,
   which client IP.

### Method B - PowerShell

```powershell
Get-AzSecurityPricing | Where-Object Name -in
    'SqlServers','SqlServerVirtualMachines','OpenSourceRelationalDatabases','CosmosDbs' |
    Select-Object Name, PricingTier

Set-AzSecurityPricing -Name 'SqlServers' -PricingTier 'Standard'

Get-AzSqlServerAdvancedThreatProtectionSetting -ResourceGroupName $Rg -ServerName $Server
```

Four sub-plan names, four independent toggles. Turning on `SqlServers` protects the
Azure SQL logical server and nothing else - not a SQL Server on a VM, not Cosmos DB.

## Validation

```powershell
# 1. Entra-only authentication is on and an admin exists
Get-AzSqlServerActiveDirectoryOnlyAuthentication -ResourceGroupName $Rg -ServerName $Server
Get-AzSqlServerActiveDirectoryAdministrator -ResourceGroupName $Rg -ServerName $Server

# 2. Firewall: your rule only, no 0.0.0.0 rule
Get-AzSqlServerFirewallRule -ResourceGroupName $Rg -ServerName $Server |
    Select-Object FirewallRuleName, StartIpAddress, EndIpAddress

# 3. Server auditing to Log Analytics, database auditing off
Get-AzSqlServerAudit   -ResourceGroupName $Rg -ServerName $Server | Select-Object LogAnalyticsTargetState
Get-AzSqlDatabaseAudit -ResourceGroupName $Rg -ServerName $Server -DatabaseName $Db |
    Select-Object LogAnalyticsTargetState, BlobStorageTargetState

# 4. Audit records are actually arriving
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId `
    -Query 'SQLSecurityAuditEvents | summarize count() by Succeeded' |
    Select-Object -ExpandProperty Results

# 5. Defender plan state
Get-AzSecurityPricing -Name 'SqlServers' | Select-Object Name, PricingTier
```

### Portal validation

Database → **Security** → **Defender for Cloud**, and **Defender for Cloud** →
**Recommendations** filtered to SQL. Those two views are what an exam question means by
"where do you see database vulnerability findings" - not the database's own metrics
blade.

## Teardown

**Mandatory.** The Defender plan and the workspace both outlive the resource group in
different ways.

### 1. Resources
- [ ] `Remove-AzResourceGroup -Name rg-sc500-lab-02-02 -Force` - server, database, and
      workspace
- [ ] `Get-AzResource -TagName 'sc500-module'` shows nothing tagged `02-02`

### 2. Subscription scope
- [ ] **Turn the Defender sub-plan off first:**
      ```powershell
      Set-AzSecurityPricing -Name 'SqlServers' -PricingTier 'Free'
      Get-AzSecurityPricing | Where-Object PricingTier -eq 'Standard'   # expect empty
      ```
- [ ] Check for orphaned role assignments left by the server's managed identity

### 3. Directory scope
- [ ] The Entra admin assignment disappears with the server. Nothing else was created.

### 4. Soft-deleted remains
- [ ] **The Log Analytics workspace is soft-deleted for 14 days.** Creating a workspace
      with the same name, resource group, and region inside that window *recovers the
      old one* rather than making a new one. Either purge it or pick a different name
      next time:
      ```powershell
      Get-AzOperationalInsightsDeletedWorkspace | Select-Object Name, ResourceGroupName
      ```
- [ ] Azure SQL keeps automated backups for the retention period; deleting the server
      removes them, but note the database would otherwise be restorable

### 5. Access
- [ ] Deactivate every PIM role activated for this lab
- [ ] Discard the SQL admin password from Part 1 - Entra-only authentication already
      made it inert, but do not leave it in a password manager as if it were live

### 6. Verify
- [ ] `Get-AzSqlServer -ResourceGroupName $Rg` errors
- [ ] `Get-AzSecurityPricing | Where-Object PricingTier -eq 'Standard'` is empty
- [ ] `Get-AzOperationalInsightsDeletedWorkspace` shows the lab workspace, and you have
      decided deliberately whether to leave it there
- [ ] Cost Management shows no new daily run rate tomorrow

```powershell
.\scripts\teardown\Remove-LabResourceGroup.ps1 -LabId '02-02' -WhatIf
```

> The sweep reports Defender plans still at Standard. It does not know about
> soft-deleted Log Analytics workspaces - that check is in the 00-03 checklist and in
> bucket 4 above.

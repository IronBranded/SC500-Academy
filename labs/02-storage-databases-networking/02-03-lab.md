# Lab 02-03 - Network Segmentation and Connectivity

**Objective:** Implement security for Azure network services
**Estimated cost:** Parts 1-2 are **cents** - two B1s virtual machines for an hour,
plus NSGs, ASGs and Virtual Network Manager, which are free. Parts 3-4 are
**walkthrough only by default**: a Virtual WAN hub and a VPN gateway bill hourly from
the moment provisioning completes, and each takes 30-45 minutes to deploy. Optional
deployments are boxed and costed where they appear.
**Licensing required:** Azure subscription.
**Time:** ~150 minutes for Parts 1-2. Add 2 hours if you choose to deploy Part 3 or 4.

> Complete **Module 0** before running this lab. Activate your roles through PIM;
> do not run labs with standing Global Administrator.
>
> **Why Parts 3 and 4 are walkthroughs.** Nothing about routing intent or an IPsec
> policy is learned better by waiting 45 minutes for a gateway to provision and then
> paying by the hour to look at it. The configuration surface is the exam content, and
> you can read all of it from the Create blade without pressing Create. Azure Firewall
> *is* deployed for real in **02-04**, where it earns its cost.

## Part 1 - NSGs and ASGs

### 1.1 Build a deliberately flat network

```powershell
$web = New-AzVirtualNetworkSubnetConfig -Name 'snet-web' -AddressPrefix '10.30.1.0/24'
$db  = New-AzVirtualNetworkSubnetConfig -Name 'snet-db'  -AddressPrefix '10.30.2.0/24'

$vnet = New-AzVirtualNetwork -Name 'vnet-sc500-0203-a' -ResourceGroupName $Rg `
                             -Location $Location -AddressPrefix '10.30.0.0/16' `
                             -Subnet $web,$db -Tag @{ 'sc500-module' = $LabId }

# Two B1s VMs, no public IP, no Bastion. You will never log in to them -
# every test below is done with Network Watcher, not with a session.
$cred = Get-Credential -Message 'Local admin for the lab VMs (not stored anywhere)'

$vmWeb = New-AzVM -ResourceGroupName $Rg -Location $Location -Name 'vm-sc500-0203-web' `
                  -VirtualNetworkName 'vnet-sc500-0203-a' -SubnetName 'snet-web' `
                  -Size 'Standard_B1s' -Image 'Ubuntu2204' -Credential $cred `
                  -PublicIpAddressName $null -OpenPorts @()

$vmDb  = New-AzVM -ResourceGroupName $Rg -Location $Location -Name 'vm-sc500-0203-db' `
                  -VirtualNetworkName 'vnet-sc500-0203-a' -SubnetName 'snet-db' `
                  -Size 'Standard_B1s' -Image 'Ubuntu2204' -Credential $cred `
                  -PublicIpAddressName $null -OpenPorts @()
```

> `New-AzVM` creates an NSG on the NIC by default. That is convenient and it is also
> the reason effective rules matter - you now have NSGs you did not write.

### 1.2 Prove the flat default

```powershell
$nw     = Get-AzNetworkWatcher -Location $Location
$nicDb  = Get-AzNetworkInterface -ResourceGroupName $Rg | Where-Object Name -like '*db*'
$ipWeb  = (Get-AzNetworkInterface -ResourceGroupName $Rg | Where-Object Name -like '*web*').IpConfigurations[0].PrivateIpAddress
$ipDb   = $nicDb.IpConfigurations[0].PrivateIpAddress

Test-AzNetworkWatcherIPFlow -NetworkWatcher $nw `
    -TargetVirtualMachineId $vmDb.Id `
    -Direction Inbound -Protocol TCP `
    -RemoteIPAddress $ipWeb -LocalIPAddress $ipDb `
    -LocalPort 1433 -RemotePort 50000
```

`Access` returns **Allow**, and `RuleName` names the default `AllowVnetInBound`. Web
can reach the database on 1433 because nothing said otherwise. Nobody configured
that - it is what no configuration means.

### 1.3 ASGs, then one rule

#### Method A - Portal

1. **Application security groups** → **Create** → `asg-sc500-0203-web`. Repeat for
   `asg-sc500-0203-db`.
2. Each VM → **Networking** → **Application security groups** → add the matching ASG.
3. **Network security groups** → the db VM's NSG → **Inbound security rules** →
   **Add**:
   - Source: **Application security group** → `asg-sc500-0203-web`
   - Destination: **Application security group** → `asg-sc500-0203-db`
   - Port 1433, TCP, **Allow**, priority 200
4. Add a second rule: source **VirtualNetwork**, destination `asg-sc500-0203-db`, any
   port, **Deny**, priority 300.

#### Method B - PowerShell

```powershell
$asgWeb = New-AzApplicationSecurityGroup -ResourceGroupName $Rg -Name 'asg-sc500-0203-web' -Location $Location
$asgDb  = New-AzApplicationSecurityGroup -ResourceGroupName $Rg -Name 'asg-sc500-0203-db'  -Location $Location

foreach ($pair in @(@{n='web';a=$asgWeb}, @{n='db';a=$asgDb})) {
    $nic = Get-AzNetworkInterface -ResourceGroupName $Rg | Where-Object Name -like "*$($pair.n)*"
    $nic.IpConfigurations[0].ApplicationSecurityGroups = @($pair.a)
    Set-AzNetworkInterface -NetworkInterface $nic | Out-Null
}

$nsgDb = Get-AzNetworkSecurityGroup -ResourceGroupName $Rg | Where-Object Name -like '*db*'

$nsgDb | Add-AzNetworkSecurityRuleConfig -Name 'allow-web-to-db-1433' -Priority 200 `
          -Direction Inbound -Access Allow -Protocol Tcp `
          -SourceApplicationSecurityGroup $asgWeb -SourcePortRange '*' `
          -DestinationApplicationSecurityGroup $asgDb -DestinationPortRange 1433 | Out-Null

$nsgDb | Add-AzNetworkSecurityRuleConfig -Name 'deny-vnet-to-db' -Priority 300 `
          -Direction Inbound -Access Deny -Protocol '*' `
          -SourceAddressPrefix 'VirtualNetwork' -SourcePortRange '*' `
          -DestinationApplicationSecurityGroup $asgDb -DestinationPortRange '*' | Out-Null

$nsgDb | Set-AzNetworkSecurityGroup | Out-Null
```

Re-run the IP flow verify from 1.2 on port 1433 (Allow, your rule) and then on port 22
(Deny, priority 300). **The rule never mentions an IP address.** Re-address either VM
and it still holds.

### 1.4 Read the effective rules, not the NSG

```powershell
Get-AzEffectiveNetworkSecurityGroup -NetworkInterfaceName $nicDb.Name -ResourceGroupName $Rg |
    Select-Object -ExpandProperty EffectiveSecurityRules |
    Select-Object Name, Access, Direction, Priority, DestinationPortRange |
    Sort-Object Direction, Priority | Format-Table -AutoSize
```

This is the list that actually governs the NIC, including defaults and anything
inherited from a subnet NSG. Keep the output - Part 2 changes it in a way no NSG can.

### 1.5 Flow logging

Do **not** try to create an NSG flow log. New NSG flow logs have been unavailable
since 30 June 2025 and the feature retires on 30 September 2027.

In the portal: **Network Watcher** → **Flow logs** → **Create**. Note that the
**Target resource type** offers **Virtual network**, and read the deprecation banner
on the NSG option. Enabling virtual network flow logs needs a storage account; if you
want the full pipeline, do it in 04-03 where the workspace and traffic analytics
already exist. What matters here is knowing which log survives.

## Part 2 - Virtual Network Manager

Free, and the most exam-relevant part of this lab.

### 2.1 Create the manager and a network group

#### Method A - Portal

1. **Virtual Network Manager** → **Create**. Name `avnm-sc500-0203`, region as usual.
2. **Scope**: your subscription. **Features**: tick **Connectivity** and **Security
   admin**.
3. After creation → **Network groups** → **Create** → `ng-sc500-0203-all`.
4. **Add virtual networks** → static membership → add `vnet-sc500-0203-a`.
5. Then look at **Create Azure Policy** on the same blade - that is dynamic
   membership, where a VNet joins the group automatically by matching a condition.

#### Method B - PowerShell

```powershell
$avnm = New-AzNetworkManager -ResourceGroupName $Rg -Name 'avnm-sc500-0203' `
            -Location $Location `
            -NetworkManagerScope @{ Subscription = @("/subscriptions/$SubId") } `
            -NetworkManagerScopeAccess @('Connectivity','SecurityAdmin')

$ng = New-AzNetworkManagerGroup -ResourceGroupName $Rg -NetworkManagerName $avnm.Name `
                                -Name 'ng-sc500-0203-all'

New-AzNetworkManagerStaticMember -ResourceGroupName $Rg -NetworkManagerName $avnm.Name `
                                 -NetworkGroupName $ng.Name -Name 'vnet-a' `
                                 -ResourceId $vnet.Id
```

> Cmdlet names in `Az.Network` for Virtual Network Manager have changed shape across
> versions. Run `Get-Command *AzNetworkManager* ` and check `-Syntax` before scripting
> this against a different Az release.

### 2.2 A security admin rule the application team cannot undo

#### Method A - Portal

1. `avnm-sc500-0203` → **Configurations** → **Create** → **Security admin
   configuration**. Name `secadmin-sc500-0203`.
2. Add a **rule collection**, target `ng-sc500-0203-all`.
3. Add a rule:
   - Name `deny-inbound-ssh`
   - Action **Deny**, direction **Inbound**, protocol **TCP**
   - Source: **Service tag** → `Internet`; destination port **22**
   - Priority 100
4. Save. **Then go to Deployments → Deploy a configuration**, select the security
   admin configuration and the region. **Nothing is enforced until this step.**

#### Method B - PowerShell

```powershell
$cfg = New-AzNetworkManagerSecurityAdminConfiguration -ResourceGroupName $Rg `
           -NetworkManagerName $avnm.Name -Name 'secadmin-sc500-0203'

$coll = New-AzNetworkManagerRuleCollection -ResourceGroupName $Rg `
            -NetworkManagerName $avnm.Name `
            -ConfigName $cfg.Name -Name 'rc-baseline' `
            -AppliesToGroup @(@{ NetworkGroupId = $ng.Id })

# then a Deny rule for TCP/22 from the Internet service tag, and:
Deploy-AzNetworkManagerCommit -ResourceGroupName $Rg -Name $avnm.Name `
                              -TargetLocation @($Location) `
                              -ConfigurationId @($cfg.Id) `
                              -CommitType 'SecurityAdmin'
```

### 2.3 Watch it outrank the NSG

Add an NSG rule that **allows** inbound TCP/22 from the internet on the web VM's NIC,
at priority 100 - the most permissive thing an application team could write. Then:

```powershell
Get-AzEffectiveNetworkSecurityGroup -NetworkInterfaceName ($vmWeb.NetworkProfile.NetworkInterfaces[0].Id -split '/')[-1] `
                                    -ResourceGroupName $Rg
```

The security admin rule appears **above** the NSG rules in the effective rule set, and
IP flow verify on port 22 returns Deny. The NSG allow is still there, correctly
configured, and irrelevant - because the NSG never gets to run.

Now change the security admin rule's action from `Deny` to `Allow`, redeploy, and
re-test. The NSG allow takes effect, because `Allow` permits evaluation to continue.
Change it to `AlwaysAllow` and the NSG cannot deny it either. **Three actions, three
different guarantees.**

## Part 3 - Virtual WAN security (walkthrough)

> **Cost box.** A virtual hub bills hourly per scale unit, and a secured hub adds
> Azure Firewall on top, also hourly. Deploying this for a lab session is one of the
> most expensive things in the guide after Security Copilot. Walk the configuration
> surface instead; deploy only if you have budget headroom and can finish and delete
> in one sitting.

1. **Virtual WANs** → **Create** → read the blade, then **Cancel**. Note Standard vs
   Basic: Basic supports site-to-site VPN only, Standard is required for everything
   else including secured hubs.
2. **Firewall Manager** → **Virtual hubs** → read the **Security Configuration**
   options. This is where a hub becomes a *secured* hub.
3. Open the documentation on **routing intent and routing policies** and answer, on
   paper:
   - Which policy inspects VNet-to-VNet and branch-to-branch traffic?
   - Which inspects internet-bound traffic?
   - In **Forced Tunnel** mode, what happens if no `0.0.0.0/0` route is learnt from
     on-premises, an NVA, or a static route?
   - A secured hub advertises the RFC 1918 ranges by default. Name one thing that
     surprises.
4. Sketch the topology you would build for: two regions, four spokes, inspection of
   all private traffic, internet egress through the hub firewall. Name every routing
   policy you would enable and where.

The sketch is the deliverable. Keep it - 02-04 deploys Azure Firewall for real and
you will want to compare the standalone-firewall topology with the secured-hub one.

## Part 4 - VPN security (walkthrough)

> **Cost box.** A VPN gateway takes 30-45 minutes to provision and bills hourly from
> the moment it finishes, regardless of traffic. There is no cheap SKU that changes
> this materially.

1. **Virtual network gateways** → **Create**. Work through the blade without creating:
   - Gateway type **VPN**, VPN type **Route-based**
   - Compare SKUs: throughput, tunnel count, zone redundancy, active-active
   - Note where **Enable active-active mode** appears and what it requires (two public
     IPs)
2. Open the **Point-to-site configuration** section of the blade and record the
   dependency that matters:

   | Tunnel type | Authentication |
   | --- | --- |
   | OpenVPN | Certificate, RADIUS, **Microsoft Entra ID** |
   | IKEv2 | Certificate, RADIUS |
   | SSTP | Certificate, RADIUS |

   **Entra ID authentication requires OpenVPN.** That is also the only configuration
   that puts VPN connections under the Conditional Access policies you built in 01-01.
3. On paper, write the custom IPsec/IKE policy you would configure for a requirement
   of "AES-256, SHA-256, DH group 14, PFS group 14, IKEv2 only, SA lifetime 1 hour" -
   name each parameter you would set.
4. Answer: your organisation requires that all internet traffic from an Azure VNet
   egress through the on-premises perimeter. Which VPN feature does that, and what is
   the failure mode if the on-premises device stops advertising a default route?

## Validation

```powershell
# 1. ASG-based rules exist and reference no IP addresses
(Get-AzNetworkSecurityGroup -ResourceGroupName $Rg | Where-Object Name -like '*db*').SecurityRules |
    Select-Object Name, Priority, Access, DestinationPortRange,
                  @{n='SrcASG';e={$_.SourceApplicationSecurityGroups.Id -ne $null}} | Format-Table

# 2. The security admin configuration is DEPLOYED, not merely saved
Get-AzNetworkManagerDeploymentStatus -ResourceGroupName $Rg -Name 'avnm-sc500-0203' `
                                     -Region @($Location) -DeploymentType 'SecurityAdmin'

# 3. Effective rules show the admin rule ahead of the NSG rules
Get-AzEffectiveNetworkSecurityGroup -NetworkInterfaceName $nicDb.Name -ResourceGroupName $Rg |
    Select-Object -ExpandProperty EffectiveSecurityRules | Select-Object -First 5 Name, Access, Priority

# 4. IP flow verify agrees with the effective rules
Test-AzNetworkWatcherIPFlow -NetworkWatcher $nw -TargetVirtualMachineId $vmDb.Id `
    -Direction Inbound -Protocol TCP -RemoteIPAddress $ipWeb -LocalIPAddress $ipDb `
    -LocalPort 22 -RemotePort 50000

# 5. Nothing expensive is running
Get-AzVirtualNetworkGateway -ResourceGroupName $Rg
Get-AzVirtualWan -ResourceGroupName $Rg
```

### Portal validation

VM → **Networking** → **Effective security rules**. This blade shows the admin rules
and NSG rules in evaluation order on one page, and it is the answer to any exam
question phrased "how would you determine why traffic is being blocked."

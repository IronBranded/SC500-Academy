# Lab 03-01 - AI Data Exposure and Purview DSPM

**Objective:** Implement security for AI
**Estimated cost:** **$0.** Microsoft 365 E5 tenant only. No Azure resources, nothing
billed hourly.
**Licensing required:** Microsoft 365 E5 / E5 Compliance. **Parts 3b and 4 additionally
require SharePoint Advanced Management**, which is unlocked automatically if anyone in
the tenant holds a Microsoft 365 Copilot licence, and is otherwise a paid add-on.
**Time:** ~90 minutes across **two sessions, at least 24 hours apart.** Reports do not
populate immediately and Restricted Content Discovery takes up to a day to apply.

> Complete **Module 0** before running this lab. Activate your roles through PIM.
>
> **Check your licensing before you start.** SharePoint admin center → **Data access
> governance**. If you see only activity reports and no snapshot or permission state
> reports, you are on E5 without SAM, and Parts 3b and 4 are walkthroughs. That is a
> legitimate outcome - record it rather than working around it.

## Prerequisites

- PIM activation: **SharePoint Administrator**, **Compliance Administrator**, and
  **Global Reader** (or Global Administrator for the DSPM policy creation step).
- Three test users from your ten E5 seats.
- Modules: `Microsoft.Online.SharePoint.PowerShell`, `PnP.PowerShell`.

```powershell
$TenantAdminUrl = 'https://<tenant>-admin.sharepoint.com'
Connect-SPOService -Url $TenantAdminUrl
Get-SPOTenant | Select-Object SharingCapability, DefaultSharingLinkType, ShowEveryoneExceptExternalUsersClaim
```

> **Version caution.** SharePoint Online cmdlets for Data Access Governance,
> Restricted Content Discovery, and Restricted Access Control have changed names and
> parameters more than once. Run `Get-Command -Module Microsoft.Online.SharePoint.PowerShell *DataAccess*`
> and check `-Syntax` before scripting anything below.

## Session 1

## Part 1 - Manufacture the problem

You cannot find oversharing you do not have. Build three sites that represent the three
patterns every real tenant contains.

```powershell
$sites = @(
    @{ Title = 'SC500 Project Henderson'; Url = 'sc500-henderson' }   # EEEU overshare
    @{ Title = 'SC500 Vendor Files';      Url = 'sc500-vendor'    }   # anyone-link overshare
    @{ Title = 'SC500 HR Confidential';   Url = 'sc500-hr'        }   # should never be broad
)

foreach ($s in $sites) {
    New-SPOSite -Url "https://<tenant>.sharepoint.com/sites/$($s.Url)" `
                -Owner '<you>@<tenant>.onmicrosoft.com' `
                -Title $s.Title -Template 'STS#3' -StorageQuota 1024
}
```

In the browser, for `sc500-henderson`:

1. Upload two or three documents with recognisably sensitive-sounding content -
   include something matching a built-in sensitive information type, such as a
   formatted credit card or national ID number, so classification has something to find.
2. **Share the site** with **Everyone except external users**, Edit permission.
3. On one document, create an **Anyone with the link** sharing link.

For `sc500-vendor`: create an **Anyone** link on a document and note the expiry.

For `sc500-hr`: leave it correctly restricted. It is your control group - a site that
*should* appear in no oversharing report.

> Do this with real-shaped but fake content. Never place genuine customer or employee
> data in a lab tenant.

## Part 2 - Close the front door for future sharing

Fixing what exists is Part 4. This part stops the bleeding.

### Method A - Portal

1. **SharePoint admin center** → **Policies** → **Sharing**.
2. **File and folder links**: default link type → **Specific people**.
3. **Advanced settings for "Anyone" links**: set an expiry and restrict to view-only.
4. **Other settings** → untick **Show "Everyone except external users" claim in people
   picker**.

### Method B - PowerShell

```powershell
Set-SPOTenant -DefaultSharingLinkType Direct `
              -ShowEveryoneExceptExternalUsersClaim $false `
              -RequireAnonymousLinksExpireInDays 7 `
              -FileAnonymousLinkType View

Get-SPOTenant | Select-Object DefaultSharingLinkType, ShowEveryoneExceptExternalUsersClaim,
                              RequireAnonymousLinksExpireInDays, FileAnonymousLinkType
```

Note what this did and did not do: every *future* share is narrower, and every existing
overshare is untouched. That asymmetry is the whole shape of this objective.

## Part 3 - Find the exposure

### 3a. Activity reports (Microsoft 365 E5)

1. **SharePoint admin center** → **Reports** → **Data access governance**.
2. If prompted, **enable data collection**. Nothing exists until this has been running.
3. Run the reports for **Sharing links - "Anyone"**, **Sharing links - "People in the
   organization"**, and **Content shared with Everyone Except External Users**.

```powershell
Start-SPODataAccessGovernanceInsight -ReportEntity SharingLinks_Anyone -Name 'sc500-anyone'
Get-SPODataAccessGovernanceInsight  -ReportEntity SharingLinks_Anyone
```

Reports cover a recent window and are capped at 10,000 sites on E5. Your Henderson and
Vendor sites should appear. HR should not.

### 3b. Snapshot and permission state reports (SharePoint Advanced Management)

If SAM is available: run the **permission state report** for sites and for files. This
is the point-in-time picture of the whole permission structure, not a recent-activity
window - and it is the one that finds the 2019 overshare nobody has touched since.

If SAM is not available: open the reports blade, confirm what is greyed out, and record
which of your three test sites you would have found with activity reports alone. That
comparison is the deliverable, and it is a real finding about your own tenant.

## Part 4 - Contain, then remediate (SAM)

The two controls, applied to two different sites, on purpose.

### 4a. Restricted Content Discovery on Henderson

Requirement: the deal team keeps working; nobody finds the site through Copilot or
org-wide search while the review runs.

```powershell
Set-SPOSite -Identity 'https://<tenant>.sharepoint.com/sites/sc500-henderson' `
            -RestrictContentOrgWideSearch $true
```

**Note the time.** This takes up to 24 hours. Come back in Session 2.

Write down, now, what risk remains: every person who could open those files can still
open them. RCD changed reachability, not permissions.

### 4b. Restricted Access Control on HR

Requirement: only the HR group may access the site, overriding any existing permission
or sharing link.

```powershell
$grp = 'sc500-hr-team'    # an Entra security or Microsoft 365 group
Set-SPOSite -Identity 'https://<tenant>.sharepoint.com/sites/sc500-hr' `
            -RestrictedAccessControl $true `
            -AddRestrictedAccessControlGroups $grp
```

Sign in as a test user outside that group and confirm access is now denied even though
their permission entry still exists. **That is the difference between the two controls,
demonstrated rather than memorised.**

### 4c. Site access review

From a DAG finding, initiate a **site access review** for Henderson. The site owner is
notified and reviews SharePoint groups and individual items. Complete it as the owner
and note what the reviewer is actually shown - it is the decision surface the exam
means when it says the owner confirms whether sharing is appropriate.

## Part 5 - DSPM for AI

1. **Microsoft Purview portal** → **DSPM for AI**. Record which version your tenant
   shows - **DSPM for AI (classic)** or the newer unified **Data Security Posture
   Management (preview)**. Walkthroughs differ between them.
2. **Overview** → read the recommendations. These are the entry point, and they
   disappear once completed or dismissed - so dismiss nothing yet.
3. Action the recommendation **Secure interactions in Microsoft Copilot experiences**,
   which creates the one-click policy **DSPM for AI - Capture interactions for Copilot
   experiences**.

   **This is the most important step in the lab.** Without this collection policy, no
   prompt or response content is recorded anywhere. Activity counts exist; content does
   not.
4. Create the other two one-click policies:
   - **DSPM for AI - Detect risky AI usage** (managed in Insider Risk Management)
   - **DSPM for AI - Unethical behavior in AI apps** (managed in Communication
     Compliance)
5. Open **Policies** and confirm all three are listed with their status. Then open one
   of them in its *owning* solution - Communication Compliance - and confirm that is
   where editing happens. DSPM creates; the solution manages.
6. If any tenant user has Copilot or Copilot Chat access, generate a handful of
   interactions - including one prompt that asks about the Henderson content, so you
   can later compare what Copilot returned before and after RCD applies.

**Stop here for today.** Reports need at least 24 hours.

## Session 2 - at least 24 hours later

## Part 6 - Read what the tooling found

1. **DSPM for AI** → **Reports**. Filter by **Microsoft Copilot experiences** and by
   **Enterprise AI apps**. If the second category is empty, that is expected in a lab
   with no managed endpoints reporting browser AI usage - record it as a scope
   limitation, not a clean result.
2. **Activity explorer** in Purview: find the Copilot interactions captured by your
   collection policy. Confirm you can see prompt and response content. Then answer the
   question from the module's *Check yourself* section 4 - what could you have told an
   investigator without this policy?
3. Re-run the Henderson Copilot query from Part 5 step 6. With RCD applied, the content
   should no longer surface. Then open the site directly as the same user - **it still
   opens.** Reachability changed; access did not.

## Part 7 - The content-level control

1. **Purview** → **Information protection** → **Labels**. Create a label
   `SC500-Confidential` with **encryption**, granting a test group **View** but **not
   Extract**.
2. Apply it to one Henderson document.
3. As a user in that group: open the document - it works. Ask Copilot to summarise it -
   it refuses.

Two different users, two different sites, three different controls, three different
outcomes. Write the table yourself: for each of RCD, RAC, and label encryption, what
changed - discoverability, access, or summarisation?

## Validation

```powershell
# 1. Future sharing is narrowed
Get-SPOTenant | Select-Object DefaultSharingLinkType, ShowEveryoneExceptExternalUsersClaim,
                              RequireAnonymousLinksExpireInDays

# 2. RCD is on for Henderson and off for HR
Get-SPOSite -Identity 'https://<tenant>.sharepoint.com/sites/sc500-henderson' |
    Select-Object Url, RestrictContentOrgWideSearch

# 3. RAC is on for HR with the right group
Get-SPOSite -Identity 'https://<tenant>.sharepoint.com/sites/sc500-hr' |
    Select-Object Url, RestrictedAccessControl, RestrictedAccessControlGroups

# 4. DAG reports exist and name the sites you expected
Get-SPODataAccessGovernanceInsight -ReportEntity SharingLinks_Anyone
```

In the portal: **Purview** → **DSPM for AI** → **Policies** shows three policies
active, and **Activity explorer** returns Copilot interactions with content. Those two
views together are the answer to "how would you demonstrate AI usage is being
monitored."

## Teardown

**Mandatory**, and unusually important here: this lab deliberately creates overshared
content in a real tenant.

### 1. Resources
- [ ] Delete all three test sites:
      ```powershell
      foreach ($u in 'sc500-henderson','sc500-vendor','sc500-hr') {
          Remove-SPOSite -Identity "https://<tenant>.sharepoint.com/sites/$u" -NoWait -Confirm:$false
      }
      ```
- [ ] **Revoke every "Anyone" link you created**, before deleting the sites - a link on
      a file in a site pending deletion is still live during the retention window

### 2. Subscription scope
- [ ] Not applicable. No Azure resources.

### 3. Directory scope
- [ ] Delete the `sc500-hr-team` group if you created one for RAC
- [ ] **Keep** the tenant sharing settings from Part 2. They are hardening, not lab
      debris, and later modules assume them
- [ ] Decide deliberately about the three DSPM one-click policies. The collection policy
      is worth keeping. The Insider Risk and Communication Compliance policies generate
      alerts against real users in your tenant - disable them if nobody is triaging

### 4. Soft-deleted remains
- [ ] **Deleted SharePoint sites go to the site recycle bin for 93 days** and continue
      to count against storage. Purge them if you want the URLs back:
      ```powershell
      Get-SPODeletedSite | Where-Object Url -like '*sc500*' |
          Remove-SPODeletedSite -Confirm:$false
      ```
- [ ] Purview audit records of this lab's activity persist under your audit retention
      policy. That is correct behaviour; do not attempt to remove them

### 5. Access
- [ ] Deactivate every PIM role activated for this lab
- [ ] Remove any test user still holding access to the deleted sites

### 6. Verify
- [ ] `Get-SPOSite | Where-Object Url -like '*sc500*'` returns nothing
- [ ] `Get-SPODeletedSite | Where-Object Url -like '*sc500*'` returns nothing
- [ ] No "Anyone" links remain in the DAG activity report at the next refresh
- [ ] Cost Management is not relevant here - but confirm no Azure resource was created
      by habit

> This is the first lab whose teardown protects **your tenant's real users** rather than
> your budget. An overshared test site that survives the lab is indistinguishable from
> the problem the lab was teaching you to find.

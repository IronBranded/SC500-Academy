# Lab 03-05 - Container Platform Security

**Objective:** Implement security for application platform services
**Estimated cost:** **Medium-HIGH.** The AKS control plane may be free on the tier you pick;
**the node pool VMs are not and they bill continuously.** Defender for Containers bills for
the cluster capacity it protects while the plan is on (the pricing page gives the unit). ACR Basic is a few cents a day. Container Apps
consumption scales to zero.
**Licensing required:** Azure subscription; Defender for Containers plan for Parts 4-5.
**Time:** ~180 minutes, **one sitting, same-day teardown.**

> Complete **Module 0** before running this lab. Activate your roles through PIM.
>
> **One node, smallest size, same-day teardown.** Nothing in this objective needs a
> multi-node cluster. A forgotten node pool is the most expensive orphan in Domain 3 after
> Bastion.
>
> **Azure CLI, deliberately.** AKS is a CLI-first service and the exam's own examples use
> `az aks`. PowerShell equivalents exist in `Az.Aks` but lag on newer flags.

## Why this lab matters

Containers move fast and share a cluster, so one bad image or one over-privileged pod can
affect everything around it. The cluster's API server is itself a powerful endpoint, and a
static admin credential is a backdoor around every identity control. This lab builds a
registry and an AKS cluster without shared credentials, adds admission control, and turns on
Defender for Containers for posture and runtime findings.

## Architecture

```text
Azure Container Registry  (admin account off, anonymous pull off)
        |  pull by managed identity
        v
AKS cluster
   - local accounts disabled -> no static admin kubeconfig
   - Microsoft Entra + Azure RBAC for Kubernetes authorization
   - API server: authorized IP ranges
   - network policy
   - Azure Policy add-on -> admission control (audit, then deny)
        |
        v
Defender for Containers
   misconfigurations, vulnerabilities, runtime alerts, drift
Container Apps / Container Instances: the same questions, briefly
```

*A teaching model of what this lab builds - not a complete deployment diagram.*

## Desired security outcome

When the lab is finished, each of these statements is true - and **Validation** proves it:

- The cluster has local accounts disabled, Azure RBAC on, authorized IP ranges set and a network policy.
- The registry's admin account and anonymous pull are both off.
- Requesting the admin kubeconfig fails - the backdoor is closed.
- The Defender for Containers plan was on for the test, and teardown sets it back to Free.
- Admission control rejects a privileged pod and names the policy, instead of only reporting it.

## Part 1 - Registry first, without the shared credential

```bash
az acr create -g $RG -n $ACR --sku Basic

# Both are off by default on a new registry - confirm, and state them explicitly
az acr update -n $ACR --admin-enabled false --anonymous-pull-enabled false

az acr show -n $ACR --query "{admin:adminUserEnabled, anonymous:anonymousPullEnabled, publicNetwork:publicNetworkAccess}"
```

The admin account is a single shared credential with push rights and no identity behind it -
the storage account key from 02-01 in a different costume. It is **disabled by default**; the
recommendation exists because people enable it (some portal flows that deploy straight to
Container Instances or Container Apps ask for it). Stating it explicitly in your build means
nobody quietly turns it back on.

Import an image so there is something to scan:

```bash
az acr import -n $ACR --source mcr.microsoft.com/azuredocs/aci-helloworld:latest \
              --image helloworld:v1
```

## Part 2 - AKS, built correctly the first time

### 2.1 Create with local accounts disabled

```bash
az aks create -g $RG -n $AKS \
    --node-count 1 --node-vm-size Standard_B2s \
    --enable-aad \
    --aad-admin-group-object-ids $ADMIN_GROUP \
    --enable-azure-rbac \
    --disable-local-accounts \
    --attach-acr $ACR \
    --enable-managed-identity \
    --enable-workload-identity --enable-oidc-issuer \
    --network-plugin azure --network-policy azure \
    --generate-ssh-keys \
    --tags sc500-module=$LAB
```

Read that command back. Every flag is an exam answer:

| Flag | What it buys |
| --- | --- |
| `--enable-aad` + `--enable-azure-rbac` | Entra authentication with **Azure RBAC for Kubernetes authorization** |
| `--disable-local-accounts` | Removes the `--admin` non-auditable backdoor |
| `--attach-acr` | Grants `AcrPull` to the **kubelet identity** - no registry credential anywhere |
| `--enable-managed-identity` | No service principal secret |
| `--enable-workload-identity` | Pods reach Azure resources without stored secrets |
| `--network-policy azure` | Pod-to-pod segmentation is possible at all |

```bash
az aks show -g $RG -n $AKS --query "{localAccounts:disableLocalAccounts, aad:aadProfile.enableAzureRbac, identity:identity.type}"
```

### 2.2 Prove the backdoor is gone

```bash
az aks get-credentials -g $RG -n $AKS --admin    # expect this to FAIL
az aks get-credentials -g $RG -n $AKS            # Entra flow, succeeds
kubectl get nodes                                 # authorised by Azure RBAC
```

The first command is the one the exam cares about. On a default cluster it works, silently,
and leaves no auditable trace tying the action to a person.

> **If you had created this cluster with local accounts enabled and disabled them later, you
> would also need to rotate the cluster certificates** - otherwise credentials already
> downloaded remain valid. New cluster, no action required. Write that distinction down.

### 2.3 Azure RBAC in practice

```bash
# Least privilege for a namespace user, as an Azure role assignment - not cluster YAML
AKS_ID=$(az aks show -g $RG -n $AKS --query id -o tsv)
az role assignment create --role "Azure Kubernetes Service RBAC Reader" \
    --assignee <test-user-object-id> --scope "$AKS_ID/namespaces/default"
```

Permissions now live in Azure, subject to PIM and Conditional Access, and they disappear when
the person leaves the directory. That is the difference from Kubernetes RBAC, where the binding
lives in the cluster and outlives the employee.

### 2.4 API server exposure

```bash
MYIP=$(curl -s https://api.ipify.org)
az aks update -g $RG -n $AKS --api-server-authorized-ip-ranges $MYIP/32
```

The API server is the control plane. Exposing it publicly is the AKS equivalent of the open
RDP port from 03-04. A private cluster is the stronger answer; authorised IP ranges is the one
you can apply to an existing cluster in a lab.

## Part 3 - Admission control

```bash
az aks enable-addons -g $RG -n $AKS --addons azure-policy
```

Assign a built-in Kubernetes initiative in **audit** mode at the resource group, using the
`New-AzPolicyAssignment` pattern from
[01-03](../01-identity-access-governance/01-03-lab.md) - the Kubernetes cluster pod security
baseline standards are a good choice.

Now try to do the thing it forbids:

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: sc500-privileged
spec:
  containers:
  - name: app
    image: mcr.microsoft.com/azuredocs/aci-helloworld:latest
    securityContext:
      privileged: true
EOF
```

In audit mode it is **created**, and reported as non-compliant. Switch the assignment effect
to **deny**, wait for it to propagate, delete the pod and re-apply. Now the API server
**rejects the request** and `kubectl` shows the policy that refused it.

**That is the difference between reporting and preventing, and it happens at admission -
before anything is persisted to the cluster.** Same distinction as `Audit` versus `Deny` in
01-03, reaching into Kubernetes instead of ARM.

## Part 4 - Defender for Containers

**Cost gate.** Billed for the cluster capacity it protects, for as long as the plan is on. Enable, observe, disable.

### Method A - Portal

1. **Defender for Cloud** → **Environment settings** → subscription → **Defender plans** →
   **Containers** → **On**.
2. Open **Settings** and confirm each component:
   - **Agentless discovery for Kubernetes**
   - **Agentless container vulnerability assessment** - and **registry access**
   - **Defender sensor** (this is the eBPF agent - required for runtime detection)
   - **Agentless scanning for machines**
3. Note the dependency the exam likes: **registry access** covers images at rest;
   **running** container assessment needs agentless machine scanning plus **either** K8s API
   access **or** the Defender sensor.

### Method B - CLI

```bash
az security pricing show -n Containers --query "{tier:pricingTier}"
az security pricing create -n Containers --tier Standard
```

### 4.3 Read the findings

Wait for discovery, then:

1. **Defender for Cloud → Recommendations**, filtered to your cluster and registry.
2. **Inventory / Security Explorer** → explore repositories, images, pods, and services. This
   is the cloud security graph; container findings participate in **attack paths**.
3. Find the vulnerability findings for `helloworld:v1` in the registry, then find the same
   CVEs against the **running** container. Two paths, one engine - **Microsoft Defender
   Vulnerability Management**, the same one you met in 03-04.

## Part 5 - Runtime detection and binary drift

With the Defender sensor deployed, exec into a running pod and do something a container should
never do:

```bash
kubectl run sc500-drift --image=mcr.microsoft.com/azuredocs/aci-helloworld:latest
kubectl exec -it sc500-drift -- /bin/sh

# inside the container - fetch and run a binary that is not part of the image
# (use something harmless; the point is that it did not come from the image)
```

**Binary drift detection** should alert: a process is running inside the container that did not
come from its image.

Then answer the question that explains why this works at all: on a VM, a new binary appearing
is ambiguous - administrators install things. In a container it is close to definitional
evidence of compromise, **because a container is supposed to be exactly its image and nothing
else.** Tighter platform constraints produce cleaner detections.

If **binary drift blocking** (preview) is available to you, enable it and repeat. Alerting and
blocking are separate settings, exactly like IDPS modes in 02-04. **Anti-malware detection
and blocking** works the same way, through anti-malware policies.

## Part 6 - ACI and Container Apps (short)

These are tested lightly compared with AKS, and the controls are ones you already know.

```bash
# Container Apps: internal ingress, managed identity, no registry credential
az containerapp env create -g $RG -n cae-sc500-0305 -l $LOCATION
az containerapp create -g $RG -n ca-sc500-0305 --environment cae-sc500-0305 \
    --image $ACR.azurecr.io/helloworld:v1 \
    --ingress internal --target-port 80 \
    --system-assigned \
    --registry-server $ACR.azurecr.io --registry-identity system
```

Confirm three things and move on:

- Ingress is **internal**, not external - the default is convenience
- The app pulls from ACR using its **managed identity**, not a registry credential
- Secrets, if any, would come from **Key Vault**, not from environment variables in the
  deployment definition

For ACI, read the **confidential containers** option in the create blade without deploying -
it is the container analogue of the confidential VM from 03-04, and that is the level at which
it is tested.

```bash
metadata: {name: sc500-validate-privileged}

  containers:
  - {name: app, image: mcr.microsoft.com/azuredocs/aci-helloworld:latest, securityContext: {privileged: true}}

# expect rejection naming the policy
```

### Portal validation

**Defender for Cloud → Security Explorer**, querying containers exposed to the internet with a
high-severity vulnerability. That query is the whole argument for the cloud security graph: a
vulnerability plus an exposure path is a different finding from either alone.

## What just happened?

- **Disabling local accounts forces every user through Microsoft Entra ID**, where Conditional Access and Azure RBAC apply. The static admin credential no longer exists.
- **Admission control stops a bad request at the API server.** In audit mode the privileged pod was created and reported; in deny mode it was refused.
- **The registry is part of the attack surface.** A shared admin password or anonymous pull lets anyone fetch, or with the password push, images.
- **Defender combines findings.** A vulnerable image plus an exposure path is a more urgent finding than either alone.

## Limitations

- Admission control checks what is submitted. It does not see what a running container does afterwards - runtime protection does.
- Defender for Containers bills for the cluster capacity it protects while the plan is on, and node pools bill continuously - teardown the same day.
- Docker Content Trust is being removed (31 March 2028). Image signing moves to Notary Project signatures.

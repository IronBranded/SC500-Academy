# Lab 03-06 - Serverless, Web, and API Security

**Objective:** Implement security for application platform services
**Estimated cost:** **Medium.** App Service Basic is cents per hour and Functions on
consumption is near-free. **Application Gateway WAF v2 bills hourly plus capacity units** and
is the expensive part. **Front Door Premium is not used** - its monthly floor does not suit a
self-funded lab, so it appears as a comparison walkthrough.
**Licensing required:** Azure subscription.
**Time:** ~180 minutes. Parts 1-3 are cheap and can be done separately; **Parts 4-5 are the
metered ones and should be done in one sitting.**

> Complete **Module 0** before running this lab. Activate your roles through PIM.
>
> **Start a timer when the Application Gateway finishes deploying.** It takes 10-20 minutes,
> and billing starts when it lands.

## Why this lab matters

Web apps, functions, Logic Apps and APIs are reachable from the internet the moment they are
created - nobody has to open a port. Each has its own trap: a deployment site with separate
restrictions, a function key that identifies nobody, a trigger URL that is itself the
credential, a WAF left in detection mode, or a gateway the backend does not require. This lab
closes each one and proves it.

## Architecture

```text
Internet
   |
   +--> Application Gateway WAF v2 (Detection -> Prevention, DRS)
   |
   +--> API Management (Basic v2)
   |       validate-jwt -> rate-limit-by-key -> ip-filter
   |       authentication-managed-identity (the gateway proves who it is)
   |            |
   |            v
   +--> App Service  (HTTPS only, TLS minimum, FTP off)
   |       access restrictions: main site AND SCM (Kudu) site
   |       App Service authentication: only the gateway's identity
   |       managed identity + Key Vault references (no secrets)
   |
   +--> Function App: keys versus identity
   +--> Logic App: the trigger URL is the credential
```

*A teaching model of what this lab builds - not a complete deployment diagram.*

## Desired security outcome

When the lab is finished, each of these statements is true - and **Validation** proves it:

- The web app is HTTPS only, enforces a TLS minimum, has FTP disabled, and restricts both the main site and the SCM site.
- The app uses a managed identity, and its settings hold Key Vault references instead of secrets.
- The WAF policy is in Prevention mode with the expected rule set.
- Calling the backend directly returns 401; calling it through API Management works.
- No Application Gateway or API Management instance is left running.

## Part 1 - App Service: the two sites people forget is two

### 1.1 Deploy and harden transport

```powershell
$plan = New-AzAppServicePlan -ResourceGroupName $Rg -Name "asp-sc500-0306" `
            -Location $Location -Tier 'Basic' -NumberofWorkers 1 -WorkerSize 'Small'

$web = New-AzWebApp -ResourceGroupName $Rg -Name $App -Location $Location `
           -AppServicePlan $plan.Name

Set-AzWebApp -ResourceGroupName $Rg -Name $App -HttpsOnly $true `
             -MinTlsVersion '1.2' -FtpsState 'Disabled' -AssignIdentity $true

Get-AzWebApp -ResourceGroupName $Rg -Name $App |
    Select-Object Name, HttpsOnly, @{n='TLS';e={$_.SiteConfig.MinTlsVersion}},
                  @{n='FTP';e={$_.SiteConfig.FtpsState}}, @{n='Identity';e={$_.Identity.Type}}
```

Note that the app had a public DNS name and was reachable **before you configured anything**.
That is the PaaS difference from 03-04: nobody opened a port, and it is open.

### 1.2 Restrict the main site

```powershell
Add-AzWebAppAccessRestrictionRule -ResourceGroupName $Rg -WebAppName $App `
    -Name 'allow-my-ip' -Priority 100 -Action Allow -IpAddress "$MyIp/32"
```

Browse the site from your address: it works. From a phone on cellular: blocked.

### 1.3 Now the trap

```powershell
# The SCM / Kudu advanced tools site has its OWN rule set
Get-AzWebAppAccessRestrictionConfig -ResourceGroupName $Rg -WebAppName $App |
    Format-List MainSiteAccessRestrictions, ScmSiteAccessRestrictions, ScmSiteUseMainSiteRestrictionConfig
```

From your phone, browse to `https://<app-name>.scm.azurewebsites.net`. **It answers.** The
deployment and console site was never restricted - and it is the more dangerous of the two,
because it offers file access and a command console.

```powershell
Update-AzWebAppAccessRestrictionConfig -ResourceGroupName $Rg -WebAppName $App `
    -ScmSiteUseMainSiteRestrictionConfig
```

`-ScmSiteUseMainSiteRestrictionConfig` is a switch: its presence turns the setting on, and
it takes no `$true` value.

Re-test. **Write this one down** - "main site locked, SCM site open" is a real finding and a
reliable exam distractor.

### 1.4 Platform authentication and Key Vault references

1. Portal → the web app → **Authentication** → **Add identity provider** → **Microsoft** →
   restrict access to **Require authentication**, unauthenticated requests → **HTTP 401**.
2. Browse the site. You are challenged **before any application code runs** - the app does not
   implement this and cannot bypass it.
3. Create a Key Vault secret and reference it from configuration rather than storing a value:

```powershell
# Grant the app's managed identity read access, then reference the secret
$app = Get-AzWebApp -ResourceGroupName $Rg -Name $App
New-AzRoleAssignment -ObjectId $app.Identity.PrincipalId `
                     -RoleDefinitionName 'Key Vault Secrets User' -Scope $kvResourceId

Set-AzWebApp -ResourceGroupName $Rg -Name $App -AppSettings @{
    'DbPassword' = "@Microsoft.KeyVault(SecretUri=https://<vault>.vault.azure.net/secrets/db-conn/)"
}
```

Configuration now holds a **reference**, not a value. Anyone reading app settings with
Contributor sees a URI.

## Part 2 - Functions: the key that identifies nobody

```powershell
$func = New-AzFunctionApp -ResourceGroupName $Rg -Name $Func -Location $Location `
            -StorageAccountName '<a storage account>' -Runtime 'PowerShell' `
            -FunctionsVersion 4 -OSType Windows -IdentityType SystemAssigned
```

Create an HTTP-triggered function at authorization level **function**, then:

1. Call it **without** the key - rejected.
2. Call it with `?code=<key>` - accepted.
3. Now ask the questions that matter: which user made that second call? Can you revoke access
   for one caller without breaking the others? When does that key expire?

The answers are none, no, and never. **A function key is the SAS token problem from 02-01 in a
new place** - a bearer credential with no identity, frequently living in a URL.

4. Replace it: enable **App Service authentication** on the Function App and set the function's
   authorization level to **anonymous**, so the platform enforces Entra authentication instead
   of a key. Call it with a token and confirm the caller is now a principal.

## Part 3 - Logic Apps: the trigger is the endpoint

1. Create a Consumption logic app with a **When an HTTP request is received** trigger and a
   trivial action.
2. Save, then copy the **callback URL**. Look closely at it - it contains a shared access
   signature. **Anyone with this URL can run your workflow.** It is a credential, not an
   address.
3. Fire it with `Invoke-RestMethod` from an unauthenticated shell to prove it.
4. Now apply the three mitigations in order and re-test after each:
   - **Trigger IP restriction** - workflow settings → allowed inbound IP addresses → your
     address only
   - **Microsoft Entra OAuth** validation on the request trigger - a policy specifying issuer
     and audience
   - Note where you would place **API Management** in front so the callback URL is never the
     public entry point
5. Turn on **secure inputs and outputs** on an action carrying a sensitive parameter, then open
   the run history and confirm the value is suppressed. Run history is otherwise readable by
   anyone who can view the workflow.
6. Replace any connection string with a **managed identity** connection.

## Part 4 - Web Application Firewall

> **Cost clock starts here.** Application Gateway WAF v2 bills hourly plus capacity units.

### 4.1 Deploy in detection mode, deliberately

Create an **Application Gateway WAF v2** in front of the App Service backend, with a WAF policy
attached. Leave the policy at its default - **Detection**.

```powershell
(Get-AzApplicationGatewayFirewallPolicy -ResourceGroupName $Rg -Name '<policy>').PolicySettings |
    Format-List Mode, State, RequestBodyCheck
```

### 4.2 Attack it and observe nothing happen

Send obvious probes through the gateway's public address:

```powershell
$fqdn = '<appgw-public-ip-or-dns>'
Invoke-WebRequest "http://$fqdn/?id=1' OR '1'='1"          -SkipHttpErrorCheck
Invoke-WebRequest "http://$fqdn/?q=<script>alert(1)</script>" -SkipHttpErrorCheck
```

Both **succeed**. Check the WAF logs and confirm both were detected and logged.

**That is the single most important observation in this part.** A WAF in detection mode
produces a dashboard full of detected attacks and blocks none of them. Microsoft's own wording
is that detection mode provides no protection.

### 4.3 Switch to prevention

```powershell
$pol = Get-AzApplicationGatewayFirewallPolicy -ResourceGroupName $Rg -Name '<policy>'
$pol.PolicySettings.Mode = 'Prevention'
Set-AzApplicationGatewayFirewallPolicy -InputObject $pol
```

Re-run both requests. Now 403.

### 4.4 Tune, using the right tool

Send a request carrying a long authorization-style header - the classic false positive, because
a token looks like an injection payload to a generic rule. It is blocked.

Fix it three ways and compare:

| Option | Effect | When |
| --- | --- | --- |
| **Exclusion** on that request attribute | The rule still applies everywhere else | **Right answer** |
| **Disable the rule** | Rule stops protecting all traffic | Blunt |
| **Custom rule** to allow | Your own condition and priority | For allow-lists and rate limits |

Apply the exclusion, confirm the legitimate request passes and the injection probe from 4.2 is
still blocked.

### 4.5 The version trap

Note in the managed rules blade which rule set version is applied - **DRS 2.2** is the
recommended version for new policies; DRS 2.1 and CRS 3.2 are older. Then record the warning:
**when you change the rule set version in the portal, your rule-state overrides, action
overrides and rule-level exclusions are reset to the new version's defaults.** PowerShell, the
Azure CLI, REST or a template can carry them across. Either way, upgrading a rule set is a
re-tuning exercise, not a version bump.

### 4.6 Front Door, by comparison only

Do not deploy it. In the portal, open **Front Door and CDN profiles → Create** and record:

- Managed rules require the **Premium** tier
- The **Bot Manager rule set** (Premium) categorises bots as good, bad or unknown
- **Standard** supports custom rules only
- **Rate limiting** is configured through **custom rules** (Application Gateway WAF supports
  rate-limit custom rules too)
- Front Door is global and at the edge; Application Gateway is regional and inside your VNet

Then answer: for an application served in one region to users worldwide, with a requirement to
rate-limit per client IP and block bad bots, which would you choose and why?

## Part 5 - API Management in front of the backend

```powershell
$apim = New-AzApiManagement -ResourceGroupName $Rg -Name "apim-sc500-0306-$((Get-Random -Maximum 999))" `
            -Location $Location -Organization 'SC500 Lab' -AdminEmail 'you@example.com' `
            -Sku 'BasicV2'
```

Import the Function App or web app as an API, create a product and two subscriptions, then
apply policies at the API level:

```xml
<policies>
  <inbound>
    <base />
    <ip-filter action="allow">
      <address>YOUR.IP.HERE</address>
    </ip-filter>
    <validate-jwt header-name="Authorization" failed-validation-httpcode="401">
      <openid-config url="https://login.microsoftonline.com/<tenant-id>/v2.0/.well-known/openid-configuration" />
      <audiences><audience>api://sc500-0306</audience></audiences>
    </validate-jwt>
    <rate-limit-by-key calls="10" renewal-period="60"
                       counter-key="@(context.Subscription.Id)" />
  </inbound>
</policies>
```

Test each independently:

1. A request with no token - 401 from `validate-jwt`, **before the backend is touched**
2. A valid token, eleven times in a minute - the eleventh is throttled, per subscription
3. A request from another address - rejected by `ip-filter`

### 5.4 Close the bypass

The backend must accept calls that come through the gateway and nothing else. **An IP allow
list cannot say that here.** Basic v2 runs on shared infrastructure with no fixed outbound
address, and the `ApiManagement` service tag lists API Management's *control-plane*
addresses, not the addresses your gateway calls backends from. Close the bypass with
identity instead: the gateway proves who it is, and the app accepts only that identity.

1. **API Management** → **Security** → **Managed identities** → turn the **system-assigned**
   identity **On**. In **Microsoft Entra ID** → **Enterprise applications** (filter:
   *Managed Identities*), note its **Application ID** and **Object ID**.
2. Add one line to the API's inbound policy, after `validate-jwt`:

```xml
<authentication-managed-identity resource="<client-id-of-the-web-app's-Entra-registration>" />
```

   The gateway now gets a token for the backend *as itself* and puts it in the
   `Authorization` header in place of the caller's token, which `validate-jwt` has already
   checked.
3. **Web app** → **Authentication** → edit the **Microsoft** provider → **Additional checks**:
   - **Client application requirement**: *Allow requests from specific client applications* -
     the gateway identity's **Application ID**
   - **Identity requirement**: *Allow requests from specific identities* - its **Object ID**
   - **Unauthenticated requests**: **HTTP 401**

   The app is now an API backend: the interactive sign-in from 1.4 no longer works for it, by
   design.
4. Remove the IP rule from 1.2. It would block the gateway too, and identity now does its job:

```powershell
Remove-AzWebAppAccessRestrictionRule -ResourceGroupName $Rg -WebAppName $App -Name 'allow-my-ip'
```

5. Call the App Service URL directly. No token: **401**. A token for any other identity:
   rejected. Through the gateway: it works.

**This is the part that makes the other policies real.** A backend anyone can reach turns every
gateway policy into a suggestion. In production, a tier with virtual network integration
(Standard v2 or Premium v2) can also reach the backend over a private endpoint, closing the
network path as well as the identity one.

## Validation

```powershell
# 1. App Service transport and both access restriction sets
Get-AzWebApp -ResourceGroupName $Rg -Name $App |
    Select-Object Name, HttpsOnly, @{n='TLS';e={$_.SiteConfig.MinTlsVersion}}, @{n='FTP';e={$_.SiteConfig.FtpsState}}
Get-AzWebAppAccessRestrictionConfig -ResourceGroupName $Rg -WebAppName $App |
    Format-List MainSiteAccessRestrictions, ScmSiteAccessRestrictions

# 2. Managed identity present, no secrets in app settings
(Get-AzWebApp -ResourceGroupName $Rg -Name $App).Identity.Type

# 3. WAF in prevention with the expected rule set
(Get-AzApplicationGatewayFirewallPolicy -ResourceGroupName $Rg -Name '<policy>').PolicySettings.Mode

# 4. The backend refuses direct calls (PowerShell 7) - expect 401
(Invoke-WebRequest -Uri "https://$App.azurewebsites.net/" -SkipHttpErrorCheck).StatusCode

# 5. Nothing expensive left running
Get-AzApplicationGateway -ResourceGroupName $Rg | Select-Object Name, Sku
Get-AzApiManagement -ResourceGroupName $Rg | Select-Object Name, Sku
```

### Portal validation

The **WAF logs** in Application Gateway diagnostics, showing detected-and-blocked versus
detected-only requests. That distinction on one screen is the difference between the two modes,
and the answer to any question about why a WAF "did not stop" an attack.

## What just happened?

- **A web app has two sites.** The SCM (Kudu) site has its own access restrictions and offers file access and a console.
- **With Require authentication, platform authentication runs before your code.** The app cannot forget to check, because the request never reaches it unauthenticated. It establishes *who* the caller is; deciding *what* they may do is still the app's job.
- **Detection mode logs; Prevention mode blocks.** Requests that matched rules in Detection mode still reached the app.
- **A gateway is only a control if the backend requires it.** Network rules could not say "only my gateway" for a Basic v2 instance, so identity did: the gateway presents its own token, and the app accepts no other.

## Limitations

- A WAF reduces common web attacks; it does not fix vulnerable application code.
- A WAF rule set version change made in the portal resets rule overrides and rule-level exclusions; scripts and templates can carry them across.
- Function keys and Logic Apps trigger URLs are shared secrets. Anyone who has one is authorised, which is why identity-based access is preferred.

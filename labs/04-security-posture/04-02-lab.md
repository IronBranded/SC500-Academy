# Lab 04-02 - Sentinel Workspace, Roles, and Content Hub

**Objective:** Implement activity and event collection in Microsoft Sentinel
**Estimated cost:** **Low if ingestion is kept minimal - and that is a decision, not a
default.** The workspace costs nothing; data does. Part 1 sets a daily cap before a single
connector is enabled.
**Licensing required:** Azure subscription. Sentinel is billed on ingestion and retention.
**Time:** ~120 minutes.

> Complete **Module 0** before running this lab. Activate your roles through PIM.
>
> **This workspace is not disposable.** `law-sc500` lives in `rg-sc500-core` and survives
> until you abandon the lab tenant - modules 04-03 and 04-04 build on it, and 02-02, 03-04 and
> 03-06 all referenced it as the destination they would eventually use. Treat its teardown
> section differently from every other lab in this guide.
>
> **Work in the Defender portal.** The Azure portal experience for Sentinel retires
> **31 March 2027**. Building new muscle memory in a portal on a countdown is wasted effort.

## Part 1 - The workspace, and the cap before the connectors

### 1.1 Decide before you create

Three properties you cannot change afterwards, or cannot change cheaply. Write your answer to
each **before** running the command:

| Decision | Your answer | Why it is hard to reverse |
| --- | --- | --- |
| Region | | Not changeable - moving means a new workspace and a migration |
| One workspace or several | | Rules, content and correlation are all per-workspace |
| Retention | | Drives cost, and short retention destroys evidence retroactively |

### 1.2 Create it

```powershell
$law = New-AzOperationalInsightsWorkspace -ResourceGroupName $CoreRg -Name $Law `
           -Location $Location -Sku 'PerGB2018' `
           -RetentionInDays 90 `
           -Tag @{ 'sc500-module' = 'core' }

$law | Format-List Name, Location, Sku, RetentionInDays, CustomerId
```

**90 days, not 30.** The default is shorter than the time it typically takes to notice an
intrusion, which means the earliest evidence expires before anyone goes looking for it.

### 1.3 The daily cap - before anything is connected

```powershell
Set-AzOperationalInsightsWorkspace -ResourceGroupName $CoreRg -Name $Law `
    -DailyQuotaGb 1

(Get-AzOperationalInsightsWorkspace -ResourceGroupName $CoreRg -Name $Law).WorkspaceCapping
```

One gigabyte a day is generous for this lab and cheap insurance. **This is the only hard stop
on ingestion spend**, and 04-03 is the module where a misconfigured collector can run away with
your budget. The cost pipeline lag from
[00-01](../../content/00-lab-safety/00-01-cost-guardrails-and-budgets.md) means you would learn
about it the day after.

> A daily cap drops data once reached. That is the correct trade-off in a lab and a deliberate
> decision in production - know which one you are making.

### 1.4 Onboard Sentinel

```powershell
New-AzSentinelOnboardingState -ResourceGroupName $CoreRg -WorkspaceName $Law -Name 'default'
Get-AzSentinelOnboardingState -ResourceGroupName $CoreRg -WorkspaceName $Law
```

### 1.5 Connect it to the Defender portal

1. **Microsoft Defender portal** → **System** → **Settings** → **Microsoft Sentinel** (paths
   move; look for the Sentinel workspace connection).
2. Connect `law-sc500`.
3. Confirm Sentinel appears in the Defender portal navigation and that incidents, hunting, and
   content hub are reachable there.

> Sentinel is GA in the Defender portal **including for tenants without Defender XDR or E5**.
> If a walkthrough tells you otherwise, it predates that change.

## Part 2 - Cost controls you set once

### 2.1 Pricing tier

**Defender portal → Sentinel → Settings → Pricing.** Leave it on **pay-as-you-go** for this
lab and read the commitment tier options.

Record the asymmetry, because it is a scenario question:

- You can **increase** a commitment tier at any time - and doing so **restarts the 31-day
  commitment period**
- To **decrease** it, or return to pay-as-you-go, you must **wait until the 31 days complete**

Committing early, on guessed volume, locks you in for a month.

### 2.2 The duplicate-ingestion trap

You will connect the Defender XDR connector in 04-03. Record the rule now:

**After enabling the Defender XDR connector, disable the individual Defender product
connectors.** Leaving both on ingests the same data twice and bills for it twice - and produces
duplicate rows in every query you write afterwards.

### 2.3 Watch your own usage

```powershell
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId -Query @"
Usage
| where TimeGenerated > ago(7d)
| summarize GB = sum(Quantity)/1000 by DataType
| order by GB desc
"@ | Select-Object -ExpandProperty Results | Format-Table -AutoSize
```

Empty today. Bookmark it - it is the query you run at the end of every session from 04-03
onward, and the one that catches a runaway collector before Cost Management does.

## Part 3 - Roles

### 3.1 Assign by job, not by convenience

```powershell
$scope = $law.ResourceId
$testUser = Get-AzADUser -UserPrincipalName '<test-user>@<tenant>.onmicrosoft.com'

# The analyst role: read, investigate, and manage incidents - not edit detections
New-AzRoleAssignment -ObjectId $testUser.Id `
                     -RoleDefinitionName 'Microsoft Sentinel Responder' -Scope $scope

Get-AzRoleAssignment -Scope $scope |
    Select-Object DisplayName, RoleDefinitionName | Format-Table -AutoSize
```

### 3.2 Prove the boundary

Sign in as the test user in the Defender portal and attempt each of these. Record what happens:

| Action | Expected with Responder |
| --- | --- |
| View incidents and run queries | Allowed |
| Change an incident's severity, assign it, close it | Allowed |
| Create or edit an analytics rule | **Denied** - that is Contributor |
| Run a playbook manually | **Denied** - that is Playbook Operator |
| Create a playbook | **Denied** - playbooks are Logic Apps, needing Logic App permissions |

That last row is the one people get wrong. **Playbooks are Logic Apps**, so authoring them is
governed by Logic App permissions, not by any Sentinel role. Playbook Operator lets someone run
one; it does not let them build one.

### 3.3 The role assigned to a service, not a person

Look up **Microsoft Sentinel Automation Contributor**. It exists so that Sentinel itself can
attach playbooks to automation rules, and it is assigned **to the Sentinel service**, not to
people. If a question offers it as an analyst's role, it is the distractor.

### 3.4 Resource-context access

Work through the configuration for **resource-context RBAC**, where a workload owner sees rows
about their own resources without access to the rest of the workspace. Note where it differs
from **table-level RBAC**, which restricts access to whole tables.

The exam phrasing to match:

- "the application team must investigate their own servers" → **resource-context**
- "restrict access to one table" → **table-level**

## Part 4 - Content hub

### 4.1 Check your permission first

Installing, updating, and deleting solutions requires **Microsoft Sentinel Contributor at the
resource group level**. Confirm you have it at `rg-sc500-core`:

```powershell
Get-AzRoleAssignment -SignInName (Get-AzContext).Account.Id `
                     -ResourceGroupName $CoreRg |
    Select-Object RoleDefinitionName, Scope
```

### 4.2 Install solutions matched to what you will actually ingest

**Defender portal → Sentinel → Content hub.** Install only these three - they are what 04-03
and 04-04 need:

- **Microsoft Entra ID**
- **Azure Activity**
- **Microsoft Defender XDR**

Resist installing more. A catalogue matched to nothing is the most common Sentinel
anti-pattern, and each solution adds templates, workbooks and parsers you will scroll past
forever.

### 4.3 The mechanic everyone misses

After installing, open **Analytics** and filter to **Rule templates**.

**You have templates. You have no detections.** Installing a solution places analytics rule
*templates* in the workspace; nothing is active until you create a rule from one.

Create one active rule from a template:

1. **Analytics** → **Rule templates** → pick a low-noise Entra ID rule
2. **Create rule** → review the query, the entity mappings, the scheduling, and the threshold
3. Tune the threshold rather than accepting it, then create

```powershell
Get-AzSentinelAlertRule -ResourceGroupName $CoreRg -WorkspaceName $Law |
    Select-Object DisplayName, Enabled, Kind
```

One active rule. Now the difference between installed and enabled is something you have done
rather than read.

### 4.4 Updates

Return to Content hub and look at how solutions are versioned and updated. Record the
consequence: **an update to a solution does not rewrite the active rules you already created
from its templates.** Good, because your tuning survives - and it means your active rules do
not automatically inherit an improved template either. Reviewing updates is a recurring task.

## Validation

```powershell
# 1. Workspace exists in the CORE resource group with sensible retention and a cap
Get-AzOperationalInsightsWorkspace -ResourceGroupName $CoreRg -Name $Law |
    Format-List Name, Location, RetentionInDays, @{n='DailyCapGb';e={$_.WorkspaceCapping.DailyQuotaGb}}

# 2. Sentinel is onboarded
Get-AzSentinelOnboardingState -ResourceGroupName $CoreRg -WorkspaceName $Law

# 3. Roles assigned by job function
Get-AzRoleAssignment -Scope $law.ResourceId |
    Select-Object DisplayName, RoleDefinitionName | Format-Table -AutoSize

# 4. Exactly one active analytics rule, from a template
Get-AzSentinelAlertRule -ResourceGroupName $CoreRg -WorkspaceName $Law |
    Select-Object DisplayName, Enabled

# 5. Usage baseline - should be near zero before 04-03
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId `
    -Query 'Usage | where TimeGenerated > ago(1d) | summarize GB = sum(Quantity)/1000' |
    Select-Object -ExpandProperty Results
```

### Portal validation

**Defender portal → Sentinel → Content hub**, showing three installed solutions, and
**Analytics** showing many templates and one active rule. That contrast on two screens is the
whole of Part 4.

## Teardown

**This lab is an exception, like [00-01](../00-lab-safety/00-01-lab.md).** The workspace is
long-lived infrastructure and 04-03, 04-04 and 04-05 depend on it. Do **not** tear it down at
the end of this session.

### What to do at the end of every session from now on

- [ ] Run the `Usage` query from 2.3 and confirm ingestion matches what you expect
- [ ] Confirm the daily cap is still set
- [ ] Deactivate every PIM role activated for this lab

### Only if you are abandoning the lab tenant entirely

### 1. Resources
- [ ] `Remove-AzOperationalInsightsWorkspace -ResourceGroupName rg-sc500-core -Name law-sc500 -Force`

### 2. Subscription scope
- [ ] Remove role assignments made at the workspace scope in Part 3 - deleting the workspace
      orphans them
- [ ] Confirm no Defender plan was enabled by this lab

### 3. Directory scope
- [ ] None created.

### 4. Soft-deleted remains
- [ ] **The workspace is soft-deleted for 14 days**, and creating a workspace with the same
      name in the same resource group and region inside that window **recovers the old one,
      data and all** - the trap from
      [00-03](../../content/00-lab-safety/00-03-teardown-checklist-template.md), and the reason
      02-02 used a separate lab-scoped workspace:
      ```powershell
      Get-AzOperationalInsightsDeletedWorkspace | Select-Object Name, ResourceGroupName
      ```
- [ ] **Removing Sentinel from a workspace does not delete the workspace**, and the workspace
      keeps charging for retained data. Two separate teardown steps

### 5. Access
- [ ] Remove the test user's Responder assignment
- [ ] Deactivate every PIM role

### 6. Verify
- [ ] `Get-AzOperationalInsightsWorkspace -ResourceGroupName rg-sc500-core` errors or returns
      nothing
- [ ] `Get-AzOperationalInsightsDeletedWorkspace` reflects a deliberate decision, not an
      accident
- [ ] Cost Management shows ingestion trending to zero over the following days

> The teardown script does not touch `rg-sc500-core` and should not. That resource group holds
> the budget, the action group, the brake runbook, and now the workspace - everything the guide
> depends on rather than everything a lab created.

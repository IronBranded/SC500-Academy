## Why this lab matters

Detection depends on getting the right data in - and only the right data, because every
gigabyte costs money. Each source arrives differently: Microsoft services through connectors,
Linux and network devices through syslog and CEF, Windows through data collection rules, and
custom applications through their own tables. This lab connects each kind, filters before
ingestion, and recognises a connector that looks healthy while delivering nothing.

## Architecture

```text
Microsoft connectors (Azure activity, Entra ID, Defender XDR) --+
                                                                |
Linux forwarder VM (AMA)                                        |
   syslog + CEF --> DCR (filter) --> CommonSecurityLog ---------+
                                                                |
Windows machines (AMA; Arc first if not in Azure)               |
   DCR --> SecurityEvent ---------------------------------------+
   Windows Event Forwarding --> WindowsEvent (another table) ---+
                                                                |
Custom source --> transformation --> SC500Lab_CL ---------------+
                                                                v
                                         law-sc500 (daily cap still set)
```

*A teaching model of what this lab builds - not a complete deployment diagram.*

## Desired security outcome

When the lab is finished, each of these statements is true - and **Validation** proves it:

- Connectors are ingesting, and Defender alerts raise one incident each, not two.
- CEF data lands in the structured CommonSecurityLog table.
- Data collection rules exist and are associated with the machines they collect from.
- The custom table exists, receives data and has the plan you chose.
- The daily cap from 04-02 is still in place.

## Part 1 - Microsoft connectors, and the duplicate-incident trap

### 1.1 Connect the free and cheap ones first

**Defender portal → Sentinel → Data connectors.** Using the solutions installed in 04-02:

1. **Azure Activity** - subscription control-plane operations. Connect at subscription scope.
2. **Microsoft Entra ID** - connect **sign-in logs and audit logs**. Note which log types carry
   a charge and which do not **before** ticking them.
3. **Microsoft Defender XDR** - connect it.

### 1.2 Then check what the XDR connector changed

Open the connector list again. The individual Defender product connectors - Defender for
Endpoint, Identity, Office 365, Cloud Apps, Entra ID Protection - were **disconnected
automatically** when the XDR connector came on. They may still show as connected; no data
flows through them.

What you must check yourself is incident creation. If you connect from the connector page,
keep **Turn off all Microsoft incident creation rules for these products** ticked (in the
Defender portal those rules aren't supported at all; Defender XDR creates the incidents). If
those rules stay on:

- The same alert raises an incident from the rule **and** one from Defender XDR
- Analysts triage everything twice
- **Every incident count you report afterwards is wrong**

Cost: Defender XDR alerts and incidents (`SecurityAlert`, `SecurityIncident`) are free. Raw
advanced hunting tables, if you tick them under **Connect events**, are billed - leave them off
in this lab.

### 1.3 Establish the baseline

```powershell
Start-Sleep 900   # give ingestion time to start

Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId -Query @"
Usage
| where TimeGenerated > ago(1d)
| summarize GB = round(sum(Quantity)/1000, 3) by DataType
| order by GB desc
"@ | Select-Object -ExpandProperty Results | Format-Table -AutoSize
```

**Write these numbers down.** You will compare against them after Part 2, which is the part
that can multiply them.

## Part 2 - Syslog and CEF

### 2.1 Build a forwarder

```powershell
$cred = Get-Credential -Message 'Local admin for the forwarder (not stored anywhere)'

$fwd = New-AzVM -ResourceGroupName $Rg -Location $Location -Name 'vm-sc500-0403-fwd' `
                -Size 'Standard_B1s' -Image 'Ubuntu2204' -Credential $cred `
                -OpenPorts 22 -Tag @{ 'sc500-module' = $LabId }
```

This machine is the pattern the exam tests: a firewall, a switch, and a security appliance all
speak syslog and **none of them will ever run an agent**. One Linux forwarder carries AMA and
receives from all of them.

> Restrict SSH to your own address and delete this VM today. It is a lab forwarder with an open
> management port.

### 2.2 Connect CEF via AMA - and filter in the DCR

**Data connectors → Common Event Format (CEF) via AMA → Open connector page → Create data
collection rule.**

1. Add `vm-sc500-0403-fwd` as a resource.
2. **Select facilities and severities deliberately.** The default breadth is the wrong answer.
   Pick two or three facilities and severity `LOG_WARNING` and above.
3. Create.

**Stop and note what you just did.** The filter lives in the DCR and is applied by the agent,
which means filtered messages are **never sent, never ingested and never billed**. That is the
single most effective cost control in Sentinel, and it is also irreversible for data that
arrives while the filter is in place.

### 2.3 Run the installer and send test data

On the forwarder, run the installation script the connector page provides, then use Microsoft's
CEF validation script to generate sample messages. Then:

```powershell
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId -Query @"
CommonSecurityLog
| where TimeGenerated > ago(30m)
| project TimeGenerated, DeviceVendor, DeviceProduct, Activity, SourceIP, DestinationIP
| take 20
"@ | Select-Object -ExpandProperty Results | Format-Table -AutoSize
```

Then compare the two tables:

```powershell
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId -Query @"
union withsource=Table Syslog, CommonSecurityLog
| where TimeGenerated > ago(30m)
| summarize count() by Table
"@ | Select-Object -ExpandProperty Results
```

`Syslog` holds unstructured messages; `CommonSecurityLog` holds parsed, named CEF fields. That
difference is why security vendors emit CEF and why it is worth the extra configuration.

### 2.4 Prove the filter works

Send messages at a severity you excluded. They do not appear. Re-run the `Usage` query from 1.3
and compare against your baseline - this is the moment the cost model becomes concrete.

## Part 3 - Windows Security events and WEF

### 3.1 Build the DCR and read the choices

**Data connectors → Windows Security Events via AMA → Create data collection rule.**

Work through the event set options **without committing to All events**:

| Set | Record your estimate of volume | What it would cost you |
| --- | --- | --- |
| All events | | |
| Common | | |
| Minimal | | |

Then select **Custom** and write an XPath filter for a specific set of event IDs - for example
failed and successful logons and privilege assignment:

```
Security!*[System[(EventID=4624 or EventID=4625 or EventID=4672)]]
```

**This is the exam-relevant option.** "Collect only these event IDs" is an XPath question, not
a predefined-set question.

> **The asymmetry, stated once more.** The analytics rule you enabled in 04-02 depends on
> specific event IDs. Filter them out and the rule produces nothing, forever, silently. Before
> you finalise an XPath filter, open your active rules and check what they query.

If you have a Windows machine available - the 03-04 VM pattern, or an Arc-enabled server -
associate it and confirm `SecurityEvent` fills. If not, create the DCR, inspect it, and move
on; the configuration surface is the content.

### 3.2 WEF, and why it is separate

Read the **Windows Forwarded Events** connector. Record the architecture:

- Endpoints forward to a **collector** using Windows Event Forwarding
- Events land in the collector's **ForwardedEvents** channel
- AMA on the collector ships them - **one agent, many contributing machines**
- Endpoints need no Azure connectivity at all

Then record the two traps:

1. **Different table.** Windows Forwarded Events writes to **`WindowsEvent`**, including
   forwarded Security log events. Windows Security Events via AMA writes to
   **`SecurityEvent`**. Open two built-in Windows analytics rule templates and note which
   table they query - a rule reading `SecurityEvent` never sees forwarded events unless you
   adapt it (or use ASIM parsers).
2. **Duplicates.** Collecting the same machine through both connectors ingests the same
   events twice, into two tables. Duplicate rows, duplicate cost - the same failure as 1.2, in
   a different place.

## Part 4 - A custom table, with a transformation

For a source with no connector.

### 4.1 Create the table

**Azure portal → `law-sc500` → Tables → Create → New custom log (DCR-based).**

1. Table name `SC500Lab_CL`.
2. Create a **data collection rule** and a **data collection endpoint** - custom logs need the
   DCE, and ingestion fails quietly without it.
3. Upload a small sample JSON file so the schema can be inferred.

### 4.2 Write a transformation

In the transformation editor, apply a KQL transformation that does two things:

```kusto
source
| where severity != "debug"          // drop low-value rows before they are billed
| project-away internalTraceId       // drop a column you do not need
| extend TimeGenerated = todatetime(eventTime)
```

Then state what you have done: the data is **reshaped before it is stored**, so you pay for what
you keep rather than what arrived - and what the transformation drops is **gone**, not hidden.

### 4.3 Send data and query it

Post sample records to the **Logs Ingestion API** endpoint using the DCE URI and a service
principal with the Monitoring Metrics Publisher role on the DCR, then:

```powershell
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId `
    -Query 'SC500Lab_CL | take 20' | Select-Object -ExpandProperty Results
```

Confirm the dropped column is absent and the debug rows never arrived.

### 4.4 Table plans

In the Defender portal, open **Microsoft Sentinel → Configuration → Tables** for the Sentinel workspace,
switch `SC500Lab_CL` from the **analytics tier** to the **data lake tier** and record what
changes (new tables and tier switches can take 90-120 minutes to settle):

| | Analytics tier | Data lake tier |
| --- | --- | --- |
| Full KQL | | |
| Usable by analytics rules | | |
| Relative ingestion cost | | |

**Detection-grade data in the analytics tier, verbose supporting telemetry in the data lake.**
Everything in Analytics because it was the default is the most common Sentinel cost mistake
after over-collection.

## Validation

```powershell
# 1. Connectors ingesting, and nothing duplicated
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId -Query @"
Usage
| where TimeGenerated > ago(1d)
| summarize GB = round(sum(Quantity)/1000,3) by DataType
| order by GB desc
"@ | Select-Object -ExpandProperty Results | Format-Table -AutoSize

# 2. CEF landing in the structured table
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId `
    -Query 'CommonSecurityLog | where TimeGenerated > ago(1h) | count' |
    Select-Object -ExpandProperty Results

# 3. DCRs exist and are associated
Get-AzDataCollectionRule -ResourceGroupName $Rg | Select-Object Name, Location
Get-AzDataCollectionRuleAssociation -TargetResourceId $fwd.Id | Select-Object Name

# 4. Custom table exists with the expected plan
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId `
    -Query 'SC500Lab_CL | take 5' | Select-Object -ExpandProperty Results

# 5. The cap is still in place
(Get-AzOperationalInsightsWorkspace -ResourceGroupName $CoreRg -Name $Law).WorkspaceCapping
```

### Portal validation

**Defender portal → Sentinel → Data connectors**, showing each connector's status and last-seen
time. A connector that shows connected with no data received is the failure this lab teaches you
to recognise.

## What just happened?

- **Data collection rules decide what is collected and where it goes.** Filtering in the rule means unwanted events are never ingested or billed.
- **CEF is structured syslog.** Parsed CEF lands in CommonSecurityLog; plain syslog lands in Syslog.
- **Forwarded Windows events land in WindowsEvent, not SecurityEvent.** Analytics rules written for SecurityEvent may not see them.
- **Transformations reshape data on the way in**, and the table plan decides cost and query capability.

## Limitations

- A connector showing Connected only means it is configured. Check last-received time and the Usage table to prove data arrives.
- Some Microsoft sources can be ingested through more than one connector; enabling both duplicates data and cost.
- The data lake tier is cheap to keep but not built for real-time analytics rules.

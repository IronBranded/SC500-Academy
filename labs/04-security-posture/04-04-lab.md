# Lab 04-04 - Sentinel Automation, Retention, and Purview Audit

**Objective:** Implement activity and event collection in Microsoft Sentinel
**Estimated cost:** **Low**, with two exceptions to watch. Logic Apps on consumption cost
pennies at lab volume. **Search jobs and restores carry their own charges, typically with
minimums** - Part 3 tells you where to stop.
**Licensing required:** Azure subscription for Sentinel. **Microsoft Purview Audit (Standard)
is included with your E5 tenant; the Audit (Premium) high-value events in Part 4 require
per-user Audit (Premium) licensing, which E5 provides.**
**Time:** ~120 minutes.

> Complete **04-02** and **04-03** first. This lab uses `law-sc500` and the connectors you
> enabled there.
>
> **The workspace is not torn down at the end of this lab either.** 04-05 needs it.

## Prerequisites

- PIM activation: **Microsoft Sentinel Contributor** on `rg-sc500-core`, **Contributor** at
  subscription scope for the Logic App, and **User Access Administrator** to grant Sentinel
  permission to run it.
- **Exchange Administrator** or equivalent for Part 4, plus Exchange Online PowerShell.
- Modules: `Az.SecurityInsights`, `Az.LogicApp`, `Az.OperationalInsights`,
  `ExchangeOnlineManagement`.

```powershell
$CoreRg   = 'rg-sc500-core'
$Law      = 'law-sc500'
$Location = 'canadacentral'
$LabId    = '04-04'
$Rg       = "rg-sc500-lab-$LabId"
$law      = Get-AzOperationalInsightsWorkspace -ResourceGroupName $CoreRg -Name $Law

New-AzResourceGroup -Name $Rg -Location $Location -Tag @{ 'sc500-module' = $LabId } -Force
```

## Part 1 - A playbook, and the permission that makes it run

### 1.1 Build the playbook

**Defender portal → Sentinel → Automation → Create → Playbook with incident trigger.**

1. Resource group `rg-sc500-lab-04-04`, name `pb-sc500-0404-enrich`.
2. **Enable a system-assigned managed identity** on the Logic App.
3. In the designer, after the **Microsoft Sentinel incident** trigger, add two actions:
   - **Add comment to incident** with some enrichment text
   - **Add tags to incident**, e.g. `auto-enriched`
4. Save.

Note what you just did with your *own* permissions: building this required **Logic App**
permissions, not a Sentinel role. Microsoft Sentinel Playbook Operator would have let you run
it and not create it.

### 1.2 Grant Sentinel permission to run it

**This is the step that breaks most first deployments.**

```powershell
# The Sentinel service needs Automation Contributor on the playbook's RESOURCE GROUP
# The portal offers this as "Manage playbook permissions" - do it there, or grant it explicitly
Get-AzRoleAssignment -ResourceGroupName $Rg |
    Where-Object RoleDefinitionName -eq 'Microsoft Sentinel Automation Contributor'
```

In the portal: **Sentinel → Automation → Configuration → Manage playbook permissions** → add
`rg-sc500-lab-04-04`.

**This is the role from 04-02 that is assigned to a service rather than a person.** Without it,
your automation rule will look correct, report no error, and do nothing.

### 1.3 Give the playbook its own permissions

The Logic App's managed identity needs access to whatever it touches. For this enrichment
playbook, Sentinel Responder on the workspace is enough:

```powershell
$pb = Get-AzLogicApp -ResourceGroupName $Rg -Name 'pb-sc500-0404-enrich'
New-AzRoleAssignment -ObjectId $pb.Identity.PrincipalId `
                     -RoleDefinitionName 'Microsoft Sentinel Responder' `
                     -Scope $law.ResourceId
```

**Record the security consequence:** a playbook that disables accounts would need directory
permissions, which would make it the most privileged object in the tenant - invokable by
anything that can trigger it. Least privilege on playbooks is not paperwork.

## Part 2 - Automation rules

### 2.1 The routing rule

**Sentinel → Automation → Create → Automation rule.**

1. Name `ar-sc500-0404-enrich`, trigger **When incident is created**.
2. Conditions: severity is Medium or High.
3. Action: **Run playbook** → `pb-sc500-0404-enrich`.
4. Order **2**. Leave the expiration indefinite for now.

### 2.2 The suppression rule, with an expiry

Create a second rule, **order 1**:

1. Name `ar-sc500-0404-suppress-lab-noise`.
2. Condition: title contains something your lab generates repeatedly.
3. Actions: **Change status → Closed**, classification **Benign positive**.
4. **Set an expiration date 30 days out.**

**Order matters and this is why.** The suppression rule runs first, closes the known-benign
incidents, and the enrichment playbook never fires on them. Reverse the order and you enrich
incidents you were about to close - wasted playbook runs and a noisier audit trail.

**The expiry matters more.** A suppression rule with no expiry is a detection you have silently
disabled, and in a year nobody will remember it exists.

### 2.3 Prove it end to end

Trigger an incident - re-run the analytics rule from 04-02, or create a test incident manually -
then:

```powershell
Get-AzSentinelIncident -ResourceGroupName $CoreRg -WorkspaceName $Law |
    Select-Object Title, Severity, Status, @{n='Labels';e={$_.Label.LabelName -join ','}} |
    Format-Table -AutoSize
```

Confirm the comment and tag arrived. Then check the playbook's run history in the Logic App -
if the rule fired and the playbook did not, revisit 1.2.

### 2.4 Break it deliberately

Remove the Automation Contributor assignment from 1.2, trigger another incident, and observe:
the rule shows as run, the playbook does not execute, and **nothing reports an error where you
would look for one.** Restore the permission.

That silent failure is the exam answer to "the playbook does not run."

## Part 3 - Retention

### 3.1 The two numbers

```powershell
# Workspace-level interactive retention
(Get-AzOperationalInsightsWorkspace -ResourceGroupName $CoreRg -Name $Law).RetentionInDays
```

In the portal: **`law-sc500` → Tables**. For each table, note **interactive retention** and
**total retention**. They are different numbers and the difference is the archive period.

### 3.2 Configure per table

Set them deliberately for two tables with opposite profiles:

| Table | Interactive | Total | Reasoning |
| --- | --- | --- | --- |
| A detection-relevant table, e.g. `SecurityIncident` | long | long | Analytics rules query it; investigations need it fast |
| A verbose table, e.g. `Syslog` or your `SC500Lab_CL` | short | long | Keep it, rarely query it |

That split is the lever that makes Sentinel affordable. Workspace-level retention alone forces
you to choose between paying interactive prices for verbose telemetry and losing detection data
early.

### 3.3 Reach past interactive retention - and stop before the bill

Open **Sentinel → Search** and look at the **search job** interface, and at **Restore** on a
table.

Record, without running one on a large table:

- A **search job** queries long-term data and writes results into a **new table**
- A **restore** brings a time range back into interactive tier for a period
- **Both take time and both cost money, typically with a minimum**

> Run a search job only against a small table over a short range, if at all. This is the one
> place in Domain 4 where an exploratory click has a floor price.

**The sentence to carry into the exam:** archived data is *retained*, not *queryable*. "We have
two years of data" and "we can query two years of data" are different claims with different
price tags.

## Part 4 - Purview Audit in the Defender portal

### 4.1 Confirm it is even on

```powershell
Connect-ExchangeOnline
Get-AdminAuditLogConfig | Select-Object UnifiedAuditLogIngestionEnabled
```

If that returns `False`, nothing else in this part works - and in a real tenant, that is a
finding in its own right. An attacker who can run
`Set-AdminAuditLogConfig -UnifiedAuditLogIngestionEnabled $false` has blinded the audit log for
the whole organisation.

### 4.2 Search from the Defender portal

**Defender portal → Audit** (audit search now lives alongside Sentinel rather than in a separate
compliance portal).

Run three searches and note what each answers:

| Search | Question it answers |
| --- | --- |
| `UserLoggedIn` for one user, last 7 days | Did this account sign in, and from where |
| `FileAccessed` / `FileDownloaded` on your 03-01 sites | What did they touch in SharePoint |
| **`MailItemsAccessed`** for one user | **Which mail data was accessed** |

### 4.3 The event that changes an investigation

Run the `MailItemsAccessed` search and read one record in full.

Three properties to note:

- It is a **mailbox auditing action** triggered when mail data is accessed **by a mail protocol
  or client**
- It fires **even when there is no explicit signal that messages were read**
- It records the **access type** - bind or sync

**Before this event existed, an investigator could establish that a mailbox had been signed
into and nothing more.** With it, you can scope which messages were exposed. That is the
difference between "an account was compromised" and a breach notification with a defensible
scope.

Then check the constraint that decides whether you get it at all:

```powershell
# Audit (Premium) events are generated only for users holding the licence
Get-MgUser -UserId '<test-user>@<tenant>.onmicrosoft.com' -Property AssignedLicenses |
    Select-Object -ExpandProperty AssignedLicenses
```

**Audit (Premium) is per-user.** An unlicensed user's mailbox produces no `MailItemsAccessed`
records, and the licensing decision was made months before the incident.

### 4.4 PowerShell and retention

```powershell
Search-UnifiedAuditLog -StartDate (Get-Date).AddDays(-7) -EndDate (Get-Date) `
                       -Operations MailItemsAccessed -ResultSize 50 |
    Select-Object CreationDate, UserIds, Operations | Format-Table -AutoSize
```

Then open **audit retention policies** and record the tiers:

| | Audit (Standard) | Audit (Premium) |
| --- | --- | --- |
| Default retention | **180 days** | **1 year** |
| Maximum | 180 days | 10 years with the add-on |
| Custom retention policies | No | Yes - per workload, record type, user |

> **Detail worth remembering:** the Audit (Standard) default changed from 90 to 180 days.
> Records generated before 17 October 2023 are kept 90 days; on or after, 180.

### 4.5 The same data, two surfaces

Query the same activity in Sentinel, where it arrived through the connectors from 04-03:

```powershell
Invoke-AzOperationalInsightsQuery -WorkspaceId $law.CustomerId -Query @"
OfficeActivity
| where TimeGenerated > ago(7d)
| summarize count() by Operation
| order by count_ desc
| take 15
"@ | Select-Object -ExpandProperty Results | Format-Table -AutoSize
```

**Audit search is the investigative surface; Sentinel is the correlation and detection
surface.** Knowing which to reach for - a targeted question about one user's activity versus a
correlated hunt across sources - is the practical skill this objective is testing.

## Validation

```powershell
# 1. Two automation rules, in the right order, one with an expiry
Get-AzSentinelAutomationRule -ResourceGroupName $CoreRg -WorkspaceName $Law |
    Select-Object DisplayName, Order, @{n='Expires';e={$_.TriggeringLogicExpirationTimeUtc}}

# 2. Sentinel can run the playbook
Get-AzRoleAssignment -ResourceGroupName $Rg |
    Where-Object RoleDefinitionName -eq 'Microsoft Sentinel Automation Contributor'

# 3. The playbook has its own least-privilege identity
(Get-AzLogicApp -ResourceGroupName $Rg -Name 'pb-sc500-0404-enrich').Identity.Type

# 4. Retention differentiated per table
# (portal: law-sc500 > Tables - confirm interactive and total differ where intended)

# 5. Audit ingestion on
Get-AdminAuditLogConfig | Select-Object UnifiedAuditLogIngestionEnabled
```

### Portal validation

The playbook's **run history** in the Logic App, showing runs triggered by the automation rule.
That page is where you confirm automation actually happened - the Sentinel rule view will tell
you it fired either way.

## Teardown

**The workspace stays.** 04-05 needs it. Everything in `rg-sc500-lab-04-04` goes.

### 1. Resources
- [ ] `Remove-AzResourceGroup -Name rg-sc500-lab-04-04 -Force` - the Logic App goes with it
- [ ] **Delete or disable the automation rules first**, or they will reference a playbook that
      no longer exists:
      ```powershell
      Get-AzSentinelAutomationRule -ResourceGroupName $CoreRg -WorkspaceName $Law |
          Where-Object DisplayName -like 'ar-sc500-0404*' |
          ForEach-Object { Remove-AzSentinelAutomationRule -ResourceGroupName $CoreRg `
                              -WorkspaceName $Law -AutomationRuleId $_.Name }
      ```

### 2. Subscription scope
- [ ] Remove the **Microsoft Sentinel Automation Contributor** assignment on the deleted
      resource group
- [ ] Remove the **Microsoft Sentinel Responder** assignment held by the playbook's managed
      identity on the workspace - deleting the Logic App orphans it:
      ```powershell
      Get-AzRoleAssignment -Scope $law.ResourceId | Where-Object { -not $_.DisplayName }
      ```

### 3. Directory scope
- [ ] The Logic App's system-assigned identity is deleted with it. Confirm no orphaned service
      principal remains

### 4. Soft-deleted remains
- [ ] **A search job creates a new table in the workspace.** If you ran one, that table persists
      and counts against retention and cost - delete it
- [ ] A **restore** occupies interactive tier for its configured period. Confirm it has ended
      rather than assuming
- [ ] **Do not** change audit retention policies as part of teardown. Audit records are evidence
      and shortening retention destroys it

### 5. Access
- [ ] Deactivate every PIM role activated for this lab, including Exchange Administrator
- [ ] `Disconnect-ExchangeOnline`

### 6. Verify
- [ ] `Get-AzSentinelAutomationRule` shows no `ar-sc500-0404*` rules
- [ ] `Get-AzLogicApp -ResourceGroupName $Rg` errors
- [ ] No search-job table remains in `law-sc500` unless you meant to keep it
- [ ] `Get-AdminAuditLogConfig` still shows ingestion **enabled** - you should never leave this
      lab having turned it off

```powershell
.\scripts\teardown\Remove-LabResourceGroup.ps1 -LabId '04-04' -WhatIf
```

> The one thing in this lab you must not tidy away is audit retention. Everywhere else in this
> guide, teardown means removing what you created. Here, the audit log contains the record of
> what you did - and in a real tenant, shortening it to "clean up" destroys other people's
> evidence.

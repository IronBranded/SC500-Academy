## Prerequisites

Two separate permissions, and **both are required** to provision capacity:

- **Azure Contributor or Owner** on the subscription or resource group - the capacity is an
  Azure resource
- **Security Administrator or higher** in the tenant you are onboarding

Activate both through PIM before you start. Discovering you hold only one *after* provisioning
has failed wastes session time you are paying for.

```powershell
$Location = 'canadacentral'
$LabId    = '04-05'
$Rg       = "rg-sc500-lab-$LabId"

New-AzResourceGroup -Name $Rg -Location $Location -Tag @{ 'sc500-module' = $LabId } -Force
```

## Part 0 - Walkthrough first, provision second

**Do this part with no capacity provisioned.** It is free, and it is most of the exam content.

1. Open the **Microsoft Security Copilot portal**. Without capacity you can still read the
   onboarding and settings surfaces.
2. Record the two-permission requirement for provisioning and why neither alone is sufficient.
3. Read the **workspace** creation surface: capacity reference, **geo selection for data
   residency**, data sharing settings, owner roles.
4. Read the **role model**:
   - **Copilot owner** and **Copilot contributor** are **not Entra ID roles** - they control
     access to the Copilot platform only
   - **Every user in the tenant is granted Copilot contributor by default**
   - **Security Administrator** and **Global Administrator** inherit Copilot owner
   - The owner-role set is **configurable**, and only the roles you select inherit owner
5. Read the **plugin governance** setting that controls who may add and publish **custom
   plugins**.

If your budget is tight, **stop here**. Answer the *Check yourself* questions in the module and
treat Parts 1-5 as optional. That is a defensible way to complete this objective.

## Part 2 - Workspace and roles

### 2.1 Create a workspace

**Manage workspaces → Create.** Attach the capacity you just provisioned. Note the settings that
are workspace-scoped: plugins, file settings, product and model toggles, members.

### 2.2 Restrict the default

Open the role settings and confirm the default state: **Copilot contributor is granted to every
user in the tenant.**

Narrow it. Then note precisely what you did and did not change:

- You restricted **who can use the Copilot platform**
- You changed **nothing** about what they can see once inside

### 2.3 Prove the inheritance model

This is the most important five minutes of the lab.

1. Sign in as a test user who holds a **Purview** role but **no Sentinel** role.
2. Ask a Purview-flavoured question. It answers.
3. Ask a Sentinel-flavoured question - something about incidents in `law-sc500`. **It cannot
   answer.**
4. Grant that user **Microsoft Sentinel Reader** on `law-sc500`, wait for propagation, and ask
   again.

**Security Copilot did not elevate anyone.** It inherited what the signed-in user already had.
Two analysts running the same prompt legitimately get different answers, and an empty result
means *no data* **or** *no access* - a permissions question, not a prompt question.

### 2.4 Owner roles

Configure the **owner role set** for the workspace. Only the roles you select inherit owner.
Select the smallest set that can administer it, and note that Global Administrator should be an
emergency path rather than the working answer - the same argument as 00-02.

## Part 3 - Plugins

1. Open **Plugins** and enable, at workspace scope:
   - **Microsoft Sentinel** - point it at `law-sc500`
   - **Microsoft Defender XDR**
   - **Microsoft Entra**
2. Note that these settings are **workspace-scoped**, so a different team's workspace can have a
   different data reach in the same tenant.
3. Run one prompt that crosses two plugins - for example, asking about an Entra sign-in and a
   Sentinel incident for the same user. Watch which plugins it calls.
4. Open the **custom plugin** surface. Do not build one. Read what it can do - KQL, APIs,
   GPT-based definitions - and then open the **owner-level governance setting** that controls
   who may add and publish them.

**Record the risk in one line:** a custom plugin can reach an external API with credentials it
holds, and by default the population able to publish one is broader than you would choose. That
is the consent problem from 01-01, in a new place.

---

## Part 4 - Agents

1. Open the **agents** surface and review what is available - Microsoft agents for recurring SOC
   work, and partner agents via **Microsoft Security Store**.
2. Enable **one** agent. One.
3. Set its **preferred workspace**, an owner-level action that determines which capacity it
   draws from and which plugin set it uses.
4. Let it run once, read the output, and **disable it before you move on.**

Then answer, in writing:

- **Agents consume SCUs on a schedule.** What does an agent enabled and forgotten cost?
- Compare this to [03-02](../03-secure-compute/03-02-lab.md). What is the same about governing
  an Entra Agent ID and a Security Copilot agent, and what is different? (One you build, one you
  enable - the permission question is identical.)

## Part 5 - Capacity monitoring

Before you deprovision, look at **capacity usage**. Record what consumed SCUs in this session:
your prompts, and the agent you ran.

That view is the answer to the exam question "your SCU bill tripled and analyst usage is
unchanged" - and the first thing to check is scheduled agents, not people.

## Teardown

**Do this now. Not after a break, not tomorrow morning.**

### 1. Resources
- [ ] **Deprovision the capacity. This is the entire teardown.**
      ```powershell
      Remove-AzResourceGroup -Name rg-sc500-lab-04-05 -Force
      ```
- [ ] Confirm it is gone rather than assuming:
      ```powershell
      Get-AzResource | Where-Object ResourceType -like '*SecurityCopilot*'
      ```

### 2. Subscription scope
- [ ] No Defender plan was enabled by this lab - run the sweep anyway:
      ```powershell
      Get-AzSecurityPricing | Where-Object PricingTier -eq 'Standard'
      ```

### 3. Directory scope
- [ ] **Disable every agent you enabled.** An agent surviving the capacity it ran on is a
      configuration waiting to bill again the next time capacity exists
- [ ] Remove the **Microsoft Sentinel Reader** assignment granted to the test user in 2.3
- [ ] Decide deliberately about the Copilot contributor restriction. Keeping it is correct
      hardening; reverting it re-opens the platform to the whole directory

### 4. Soft-deleted remains
- [ ] **Session history and promptbooks persist independently of capacity.** Review what your
      prompts contained - in a real tenant this is a record of what the SOC asked and when, and
      it is worth governing rather than forgetting

### 5. Access
- [ ] Deactivate **both** PIM activations - the Azure role and the tenant security role
- [ ] Confirm no standing Security Administrator assignment was left behind

### 6. Verify - do all four
- [ ] `Get-AzResource -ResourceGroupName rg-sc500-lab-04-05` errors
- [ ] No Security Copilot capacity resource exists anywhere in the subscription
- [ ] No agent remains enabled
- [ ] **Check Cost Management tomorrow and again in three days.** SCU charges lag, and this is
      the one lab where a mistake is measured in tens of dollars rather than cents
